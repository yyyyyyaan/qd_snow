  （d3 6.809 vs 7.243 ns；d5 9.524 vs 9.603 ns），代价 LUT +10.9%/+9.9%、FF +73%/+51%
  ⇒ **执行协议在频率上中性偏正，取舍是纯面积换延迟**。
- **⚠️ 它不省面积**（NN 个 PE 全都实例化了）。它是**协议验证**。
- **两个串行协议特有 bug（都是取样时机，必须当 checklist）**：
  ① **组合跨缝信号必须按方向区别对待**：源相位**晚** ⇒ 直连活线（0 代价）；源相位**早** ⇒
  在源自己相位末锁存 F(Q_k)（**单缓冲**够用）。一律直连会 FAIL（2054 vs 2314 行）。
  ② **任何"跨全阵列的组合归约"被全局控制器消费时，不能在 `phase_last` 取样**，
  必须在**相位 0** 锁一份或按相位累加。`commit_bits` 就是这样出错的，症状是
  **状态行 2314/2314 全对、commit 却 0/6** —— 比数值不一致更难察觉的静默失败。
- **已知覆盖缺口（仍未补）**：`flip_xfer_cycles = 0`（`ser_ef` 那一路从未被数据流验证过，
  接线正确性只由"与 `ser_ep` 同构"保证）。注意：**lattice 里的同名计数器含义不同**
  （它数的是"端口由镜像 bank 服务"），不能用它宣布这个缺口已补。
- **⚠️ `SNOW_MINTS` + `SNOW_SERIAL` 是未装护栏的坑，会静默出错**（不是编译错误）：
  SERIAL 的 edge 实例把 stage 写死成 `.stage(stage)`，而 PE 实例用 `stage_eff`
  ⇒ 同开时 PE 看到 IDLE、边看到 MW/MH；且 SERIAL 那份控制器没有 `mts_last` 门控。
  **认 `ifdef` 分支名，不要认行号（会漂移）。目前没有实测需求，不要顺手加。**

### 2.8 共享 lattice 第 (b)(c) 步：**功能达成、六条逐行 PASS、面积验收线未达成**（报告 §6.20）

**结构**：每**槽位**一个数据通路实例（不是每节点/每边一个）；状态在一个共享寄存器 bank 里，
四个互不相交地址带（节点寄存器 / 节点镜像 / 边寄存器 / 边镜像）；
`NCTX` 片按相位时分复用，一个逻辑步 = `NCTX` 个相位，**全 posedge**。

**让第 (c) 步成立的唯一规则（相位不变性）**：

```
每个端口读源 cell 的状态时，与"当前正在跑的相位"比较：
    源 slice <  phase   ->  读镜像（该 slice 本 stage 已提交，镜像里是 stage 首值）
    源 slice >= phase   ->  读寄存器（本 stage 尚未提交，寄存器就是 stage 首值）
```

- 这个选择必须**动态**（与 `phase` 比较），不能是每条链路的编译期常量：常量只在
  "消费方在自己的相位被求值"时成立，而阵列输出是**跨 cell** 被读的。
- 把它同时用到"cell 自己的状态读"上之后，**每个 cell 的组合输出都相位不变，逐位等于扁平阵列的值**
  ⇒ `push`/`pulse`/`flip` 可以**活线抽头**（`cell_push[NB_C][NB_RV]`、`cell_pulse[CU]`）。
- **⇒ 计划里的"方案 B（复制一套 merging 逻辑，估 +20% 面积）根本不需要**：零寄存器、零复制比较器，
  只加一个小比较器 + 地址 mux。已写进设计文档 §4.8.2。

**关键语义判据（推翻旧结论的那一条）**：扁平阵列的 **PE 输出就是它的寄存器**
（`assign o_cid = cid`），所以 `ab_cid[n] = pe_cid[AB_S]` 是 **stage 首值**、不是次态；
golden 的缺陷**每步只降一层**（`rep d3 n=2`：T1 节点 6 → T2 节点 8 → T3 节点 10）。
读次态（`cell_nxt[AB_N]`）会让整条链在一个 step 内落地 —— 实测错。
上一轮"问题不在读、在调度"的结论，是**bank 选择规则差一格**造成的误判。

**流程缺陷（已修）**：`sweep.ps1` 的 tag 里没有切片数 ⇒ n 扫描会**逐行覆盖自己的产物**
（CSV 只留最后一次、日志被冲掉；本轮先踩到才发现）。已加 `_s<n>` 后缀（n=2 保留旧 tag），
`synth_lattice.ps1` 已把它传下去，并用 `rep d3 n=3` 实测确认（`..._xcvu9p_s3`，数字复现 1,169/506/186.0）。
与历史上"`--dirs used` 的 tag 少了 `_used`"同类。

**这一轮修掉的 13 类根因**（完整版在 `lattice_b_step_status.md` §3 / 报告 §6.20.5）：

1. 生成器 `_vec` 把所有负值写成"全 1"（只对 −1 成立）⇒ 端口地址偏 1 个字
   （实测：节点 8 指向节点 2 的端口读 `bank[25]` 而非 `bank[24]`，答 cid 0 而非 2）；
   现在按 `int(v) & ((1<<w)-1)` 发。
2. `_iarr` 给 `_vec` 传宽度 1 ⇒ 身份字/复位字被截成 1 位，整个 bank 起来全是 0。
3. **DROP 源是 `above` 的 stage 首值（bank 读），不是次态**（见上）。
4. **bank 选择规则差一格，且有两处不同错法**：节点用"源 slice ≤ 本 slice 读镜像"、
   邻居端口用"源 slice == 本 slice 读寄存器"，都改成 §2.8 的动态规则。
5. **边 DROP 源 `EB_AB` 是常量 `+EROW` 且是错的**：边的 `above` 会跨 slice、差一个 layout layer
   （实测 e2 在 +72、e6 在 +25，不是 +48；8 条里错 3 条），且无法表达镜像选择。改成"绝对地址 + 源 slice"。
6. **边 `above` 的断言是死代码**（`enumerate(dict)`，见 §1）⇒ 错常量得以存活。
7. **`EB_HA` 是"每槽位"标志，而一个槽位每 slice 各有一条边** ⇒ 用它选分支让另一 slice 的边
   读到越界下标，`'x'` 被提交进活 cell（实测 666 个轨迹值变 `'x'`）。改成每 cell 的 `EB_ABH`。
8. **`push` 抽头取自 DROP 源而不是"该方向的邻居"**：`push` 跟的是邻居**本拍**算出的 `n_ptr`，
   既不能从 bank 里的 `ptr` 重算，也不能取自 `above`（`rep d3` 里节点 4 唯一邻居是 10、`above` 是 2）。
9. **`EB_DU`/`EB_DV` 用了按层排序的 `eup`/`elow`**，而扁平阵列 `SNOW_EDIRU_VEC` 的口径是
   "U 指向 V 的方向" ⇒ `flip_u`/`flip_v` 对调；因 XOR 与加法都对称而藏了很久，直到
   golden 在 `T 3 m 1` 翻转边 4-10 的 `ecorr` 而 RTL 不翻。
10. **`busy_step_vec` 对"本拍没跑的 cell"读镜像**（上一 stage 的值）⇒ merging 只跑 1 个子轮
    就退出（golden 跑 3 个）。改成读寄存器（已提交的在寄存器里，正在跑的用组合 `busy_c`）。
11. **`commit_hold` 被两个 `always` 块驱动**（multi-driven，见 §1）⇒ 已合并进控制器块。
12. **`initial` 预置让每个 bank 字有两个常量驱动** ⇒ 改成"全 bank 一个 `initial` 清零 +
    每 cell 走时钟复位路径"。
13. **非结构 cell 未门控**：`(slot, slice)` 不属于该 slice 窗口时算出的行号越窗、地址落进**边带**；

### 2.11 折叠实验（P0′）：**空槽位在综合里是真的免费** ⇒ 面积 ∝ 活格点数（报告 §6.28）

**问题**：共享阵列**每个槽位都例化一个数据通路**，而 rotated 单基的检查点阵只占自己包围盒的 **50%**
（d21：盒 22×20=440、真实 220；未旋转是 462 槽 / 462 真实、**0% 浪费**）。
两者**槽位数几乎一样（440 vs 462）**、**真实格点差 2.10×** ⇒ "rotated 省一半面积"
完全取决于**空槽位在综合里免不免费**。

**做法**：`make_lattice_sim.py --pad K` 把**空间盒** ×K（NSLOT/ESLOT ×K），新增槽位在每个 context 里
`*_VALID = 0`；`--pad 1`（默认）**逐字节不变**（对三份改动前的缓存表实测同哈希：rep d3 n=2 /
rep d5 n=2 / surface d5 n=5）。不改 RTL、不改判据。每个 K 落自己的 tag/log/report/CSV 行。

**实测**（VU9P、5.0 ns、`-Mode synth`；`pad_fold_battery.ps1`）：

| 配置 | pad=1 | pad=2 | pad=4 |
|---|---|---|---|
| `rep d3 n=2` 实例数 | 18 | 36 | 72 |
| **LUT / FF** | **1,149 / 406** | **1,152 / 406** | **1,152 / 406** |
| `surface d3 n=2` 实例数 | 62 | 124 | 248 |
| **LUT / FF** | **4,343 / 1,241** | **4,542 / 1,224** | **4,551 / 1,223** |

- `rep`：实例 ×4 ⇒ **LUT +3（+0.26%）、FF 一位不差**，且 **pad=2 与 pad=4 层次表逐字相同**
  ⇒ 那 +3 是**一次性**地址位宽效应，**每个空槽位的边际成本 = 0**；
- `surface`：第一次翻倍 +199、第二次翻倍只 +9 ⇒ 成本**不与空槽位数成正比**；
  而那 +199 在 rotated 上**根本不会发生**（rotated 槽位空间 440 ≈ 现在 462 ⇒ 地址位宽不变）；
- **直接看见**：层次化利用率表里空实例**根本不出现**（`g_slot[4..7]/[12..15]`、`g_eslot[5..9]/[15..19]` 无 cell）；
  综合 `0 errors, 0 critical warnings, 0 warnings`。

**判决（判据跑前写死）**：**折叠成立** ⇒ **面积 ∝ 活格点数**。机制：空槽位没有状态寄存器
（`own`/`omir`/`eown` 在 `generate if (*_VALID)` 里）、没有写使能（`run = NVALID/EVALID && …`）。
⇒ d21 换 rotated 单基：**节点 2.10×（9,702→4,620）、图边 1.97×（100,038→50,838）**
⇒ **Z-7020 上 d7**（72,982→≈37K LUT）、**电路级 d21 装进一颗 VU9P**（≈1.1M→≈560K，Helios 是 n/a）。
取证：`fpga_flow/evidence/PAD_FOLD_lat1_summary.txt`。


### 2.12 P0″：电路级的**几何可行性** —— 前提**不成立**，已定位并修好（报告 §6.29）

**为什么要查**：D14 给电路级定的价只用了**图的统计量**（节点数不变、边 ×1.35/1.60/1.72、
最大度 6→12），据此说"RTL 不用改、只是表重新生成"。但共享 lattice 的编号依赖三条几何前提
（层同构 / 边 = `(layout layer, 类, anchor rank)` 且 `(slot,slice)` 是双射 / `above` 是上一层同一条边），
**它们从来没在电路级上验过**。

**检查器**：`fpga_flow/check_circuit_level_geometry.py`（**独立于生成器**，3.2 s 跑 5 配置 × 2 噪声，
输出 `logs/circuit_level_geometry.txt`）。

**结果：P1/P3 全过，P2 不成立**——旧规则下 surface d3/d5/d7 电路级分别有
**10 / 76 / 246 个 `(slot,slice)` cell 被两条边同时占用**，生成器直接
`ASSERT FAILED: two edges share cell`。**最大度 d5/d7 = 12 = NDIR，零余量**（新断言正好卡住）。

**根因**：边类原来只有三个值，**第三条"跨层"根本不检查 rank**。这对唯象图恰好正确
（跨层边永远是纯时间步），但电路级的 **hook 边**（`south down` / `east up` / `south east up`）
**跨层且变 rank**，于是落进同一个槽位。类清单每个 d 形状完全相同：**只多三类**，
`dL=+1`、`drank ∈ {−NY, +1, +NY+1}`。

**修法**：边类推广成**完整 `(Δlayer, Δrank)` 对**（平面内 `|drank|=1→0`、`=NY→1` 保留原 id ⇒
唯象逐字节不变；其余按排序给新 id），并**删掉"平面内别的 drank 就 `_die`"**（它会拒绝 rotated——
rotated 的平面内步长是 `±(NY∓1)`）。RTL 需要的两条（每层 `(类,rank)` 集合相同、`(slot,slice)` 双射）仍由断言守住。

**结果**：电路级表**第一次生成出来**：ESLOT 38→**56**（d3）、183→**312**（d5）、508→**912**（d7）；
活边 ×1.35/1.60/1.72 而实例化槽位 ×1.47/1.70/1.79（多出的是纯填充，而**填充免费**——§2.11）。
**红线全守**：三份唯象表 + 两份默认 golden 逐字节相同；**平面内放宽对未旋转列可证是 no-op**
（两版生成的电路级 d5 表完全相同）。

**两条计划修正**（已写进 §4）：
1. ⚠️ **`rep` 不能做电路级**（localuf 直接 `NotImplementedError`）⇒ **d3 电路级回归用 SURFACE d3**，
   不再有"廉价的 rep 载体"；
2. 电路级 golden 已能生成（surface d3 8,701 行），方向表头就是那 12 个（含 6 个 hook 方向）。

**还没验的**：**rotated × 电路级** —— 等 P4 第一步把 `RotatedSurface` 变成 `Code` 子类后，

**⚠️ 以下为已废弃的原 D10 内容（留痕，不要照它执行）**

`J` 的机制本身没错，被推翻的只是"用深度门槛去选 J"这条规则；机制部分仍有参考价值：

- `J` 的含义：**一个槽位（= 一个数据通路）承载 `J` 个层 ⇒ `J` 个节点/slice**，于是
  **深度 `D = J × NCTX`**。d21/n=7 ⇒ `J = ceil(16/7) = 3`，`D = 3 × 7 = 21` ✓ 过门槛。
  （另一条 (a) 是"加大 n 把 NCTX 抬到 21"，跨片端口会涨到 32%，**已否决**。）
- **三条机械后果（必须一起记，不能只记"深度够了"）**：

  | 量 | 随 J 的变化 | d21/n=7：J=1 → J=3 |
  |---|---|---|
  | 槽位 / 数据通路数 | **÷ J** | 1,386 → **462**（= 层内空间位置数 P） |
  | 深度（LUTRAM 判据） | **× J** | 7 → **21** ✓ |
  | **每轮拍数（延迟）** | **× J** | ≈4–5× 当前 → **≈12–15× 当前** ⚠️ |

  面积 ≈ `(NSLOT/J) × 数据通路` **+ 状态位**（位总量 `NSLOT × J × NCTX` **恒等于总节点数、不随 J 变**，
  只是 LUTRAM 化后每 bit 便宜得多）⇒ **组合逻辑主导的那部分是 ∝ 1/J**。

  > **不变量（用它一句话说清 J 是什么）**：`数据通路数 × 深度 = (节点 × slice) 总单元数 = 常数`。
  > 所以 **`J` 只是"每个数据通路的深度 ÷ NCTX"的别名**，调 J 就是在这条常数线上
  > **在延迟与面积之间滑动**（J=1 最快最贵，J 越大越省越慢）。
  > LUTRAM 的作用是**改变这条线的形状**：深度 ≥16 时状态存储/读选网络的成本几乎不随深度涨，
  > 于是"往 J 大的一侧滑"才开始真正省面积。
- ⚠️ **由此暴露一条比深度更硬的约束：`ns/轮`。这一条就是推翻 D10 的理由。**
  d21/n=7 本来估 **≈4–5× 当前每轮**（设计文档 §1 表；该数本身是**外推不是实测**），
  再 ×J=3 ⇒ **≈12–15× 当前 ≈ 1.0–1.4 µs/轮**。
  **预算 = ≈1 µs/轮，而且是论文自己给的**（§3.4b：d27 的 48.5 ns/轮被写成
  "over 20 times faster than the measurement rate" ⇒ 测量率 ≈0.97 µs；d51 的 543.9 ns 达标、
  1064 ns "slightly slower" 不达标——两处都指向 ≈1 µs）。
  ⇒ **J=3 落在预算的 0.75–0.94×，破线 ⇒ 否决**；
  ⇒ **J=1 的 ≈582–605 ns/轮 有 ≈1.6–1.7× 余量 ⇒ 采纳**（P0b 实测斜率，报告 §6.25）。
  ⇒ 原来挂着的"向算法侧要每轮延迟预算"**这个悬空项可以关掉了**：预算 ≈1 µs，论文口径。
- **重构时要一起定的三件（都还没做）**：
  1. 生成器的槽位/地址映射加 `J` 维：端口表按 `(slot, j, slice)` 出，
     `ROW = SLICEBASE[slice] + SLOTLAY[slot] + j`，`slot` 只覆盖 `NSLOT/J` 个位置；
  2. `phase` 从"`NCTX` 个 slice 轮转"改成"`J × NCTX` 个 `(j, slice)` 轮转"（这就是拍数 ×J 的来源）；
  3. RAM 形态选型：**J 个 depth-`NCTX` 的小 RAM** 还是**一个 depth-`J·NCTX` 的大 RAM**
     ——按 §4.9 的约束（连续赋值左值必须常量边界），**前者地址更简单**，倾向前者。
- **不受 J 影响、仍然成立的两条**：小 d（深度 2–5）上做 LUTRAM **仍是负收益**，
  **不指望原型面积下降**（D3）；**两条形态（FF / LUTRAM）都要过十条逐行回归**，
  且开关默认 = 已验的 FF 路径（红线 §5）。

**动手前必须再过一遍的三件事（第 2 件已由 D3 + D11 答完，真正还没答的是 1 和 3，别直接写 RTL）**：

1. **读口预算（我判断这是真正的难点，尚未实测）**：合并版每个 cell 要并发读几百个字
   （`surface d5 n=2` 有 ~576 个读口）。真 RAM 宏只有 1–2 个读口，
   所以"一个大 bank 换成一个 RAM"**不可能直接成立**。大概率要变成
   "每槽位一个小 RAM + 读侧本地化"，那是又一次结构性改动。**先算一遍读口数再动手。**
2. **判据与目的（✅ 已答：D3 + D11）**：§6.11 的判据是深度 ≥16，而当前原型深度只有 2/3/5，
   本来就不到门槛；§6.1 另有一句"原型即使深度只有 2 也应该走 RAM 形式"——那说的是

   d21 的外推建立"对的形态"，**不指望当前原型的面积下降**（深度 2–5 时 RAM 本来就不划算）。

- **不要直接跑 d21 全图实现级**（约 24 小时且大概率因拥塞失败）。
- ⚠️ 顺带一条边界：**"为让本机能综合出来"不足以成为动用 `J` 维（或更大 n）的理由**——
  按 **D11**，加深复用要按比例付 `ns/轮`，而 `ns/轮` 有 ≈1 µs 的硬下限。
  降规模要走 **LUTRAM**（P3），不要靠加复用。

#### 3.4 时序：**目标已放宽到 6.5 ns**（D1），以及"不要拿吞吐去比 Helios"（D6）

> **2026-09-21 更新**：6.5 ns 是 **VU9P** 口径；上板器件是 **XC7Z020（7 系列，更慢）**，
> 板上必须**用真器件重跑后按实测重新声明**（§3.7 / D12）。

**决定**：综合/实现约束从 **5.0 ns 放宽到 6.5 ns（≈154 MHz）**，新的 run 一律带
`-Period 6.5`；**`WNS ≥ 0` 不变**。依据：d7 的实测最好成绩是 **6.359 ns / 157.3 MHz**
（MINTS+BUSYREG，综合），离 5 ns 差 21%；放宽到 6.5 ns 就能以正 slack 收敛。
上板时按板上干净频率（150 MHz）重新声明并留布线余量。

**为什么放宽不是"落后 Helios"**：

| | 拍/轮 | 时钟 | **ns/轮** |
|---|---|---|---|
| 本项目 d7（实测基线） | **7.75** | 87.4 MHz | **88.7**（设计文档 §6 锚点） |
| 本项目 d7（MINTS+BUSYREG 的最好时钟） | ≈7.75×延迟代价 | 157.3 MHz | **≈49** |
| Helios d=13（论文，0.1% 现象学） | ≈1.15 | 100 MHz | **15** |
| Helios d=21 | ≈1.15 | 100 MHz | **11.5** |

- Helios 论文自述 **"targeting a clock frequency of 100 MHz"**，Table 1 的
  **d=21 fmax 就是 100 MHz**（d3 260 / d5 220 / d9 175 / d13 140 / d17 125）。
  **200 MHz 是本项目自设的**，不是他们的要求；我们的 157.3 MHz 已经高于他们的运行时钟。
- **但差距不在时钟，在拍数**：7.75 vs ≈1.15（~6.7×），时钟我们只领先 1.6×，
  净下来**同 d 落后 Helios 3–6 倍**。Helios 论文说"d 越大每轮越快"，所以 d=7 时
  他们只会比 d13 的 15 ns 更慢一点、不会更快。
- **⇒ 结论（D6）：吞吐不是本项目的竞争轴。**
  要赢只能把每轮拍数压到 1–2 拍，那等于放弃窗口流式调度、换成另一个算法
  （Helios 的分布式 UF，d=21 用 4,620 个 PE 全并行）。**不是这个项目的范围。**
  对外**只报 ns/轮，不报 MHz**，并且只在门级回归通过后引用。

**⚠️ 一条反直觉的实测结论：现有的时序杠杆买不到吞吐。**

- MINTS 是拿**面积**换**频率**：d7 +23.9% LUT、87.4 → 149.0 MHz（×1.70）；
  但它的代价是 **M/m 阶段的拍数 ×G**，每轮延迟跟着涨。
  项目记录（§2.2）的延迟倍率是 **1.44×（G=2）/ 1.88–1.91×（G=3）**；
  而 `cycles.csv` 里的 `split_factor` 是 **≈1.60**——**两套口径不同，本轮没有核对清楚**。
  按 1.9× 算 ns/轮 反而**差 ~11%**；按 1.6× 算是**好 ~6%**。
- **但无论哪个口径，净收益都在 ±10% 以内，而面积代价是 +24%（d7）。**
  ⇒ **MINTS/BUSYREG 的价值在 WNS（让 d7 能收敛），不在吞吐。**
- MINTS+BUSYREG 叠加：d7 **89,291 LUT / 6.359 ns / 157.3 MHz**（+1.3% LUT、−5.2% 周期）。
- **未实测的两条时序路**：① **d7 关调试总线**（d5 判过非瓶颈，d7 未判）；
  ② 放宽目标（**这条就是 D1，已定**）。其它五条（MINTREE / `--dirs used` / pblock /
  `keep_hierarchy` / d5 关总线）已实测排除。

#### 3.4b **Helios 是怎么做到 d=21 甚至 d=51 的**（论文原文证据；D11 的依据）

> 问："延迟高就没意义。那 Helios 怎么做到 21 码甚至 51 码？是不是 snowflake 就不能在单板上做大码距？"
> 答：**Helios 没有绕开"面积 × 时间"这条线，它站在线的另一端；而"单卡做大 d"靠的正是虚拟化。**

**① Helios 的 d=21 是"完全不虚拟化"换来的——它把整块大板填满了。**

> "without context switching we can support the distributed UF decoder with d up to 21 for
> phenomenological noise model and up to 17 for circuit level noise, **due to resource limits**.
> We use context switching only for d exceeding those limits."
> "the largest number of PEs we can implement [on] a single VCU129 FPGA is **4620 (d = 21)**"

论文 Table 1（VCU129，现象学 / 电路级）：

| d | LUT | regs | f_max | | LUT | regs | f_max |
|---|---|---|---|---|---|---|---|
| 3 | 970 | 528 | 260 | | 1,557 | 699 | 195 |
| 5 | 6,425 | 2,425 | 220 | | 11,128 | 3,469 | 130 |
| 9 | 52,111 | 13,754 | 175 | | 93,797 | 22,515 | 110 |
| 13 | 165,718 | 47,211 | 140 | | 340,084 | 74,927 | 100 |
| 17 | 448,314 | 122,028 | 125 | | 888,854 | 177,284 | 75 |
| **21** | **898,715** | **238,939** | **100** | | **n/a** | n/a | n/a |

⇒ **d=21 = 898,715 LUT**（≈76% of 一颗 VU9P 的 LUT），而**电路级 d=21 连他们都装不下**（只到 d=17）。
d=21 的 11.5 ns/轮 是"**4,620 个 PE 全并行 + 100 MHz**"买来的（11.5 ns ≈ 1.15 拍）。

**② d≥27 他们用的就是"虚拟 PE"——和我们说的 `n`/`J` 是同一个东西。**

> "Helios can optimize for resource usage by **mapping multiple virtual PEs to a single
> physical PE**"；"Helios-8 will have a lattice with a height of four physical PEs, but the PEs
> in the topmost layer would only have **three virtual PEs mapped to each physical PE**"；
> "**context-switchings**"；"each physical PE **cycles through** a single measurement result of
> the corresponding ancilla in each context"

⇒ 这就是我们的"**NCTX 个 context 共享一个数据通路 + 相位轮转**"。

**③ 虚拟化的代价近似线性——和我们的 `×J` 是同一个量级（这是最重要的一条）。**

| 配置 | 虚拟 PE / 物理 PE | LUT | ns/轮 |
|---|---|---|---|
| d=27 | 4 | — | **48.5**（"over **20 times faster** than the measurement rate"） |
| d=27 | 27 | **173,000** | **360** |
| d=51 | （重度） | **796,000**，**85 MHz**（利用率把频率压下来了） | **543.9**（p=0.001）/ **1064**（p=0.005，**"slightly slower than the rate of measurement"**） |

4→27（6.75×）换 48.5→360（7.4×）：**≈线性**。而且 **d=51 在 p=0.005 时他们自己也不达标**。

**④ 他们的面积是 O(d³) 增长的**：论文原话 "the numbers of vertices and edges grow by O(d³)"
⇒ **大 d 单卡必然要虚拟化**。这不是雪花的问题，是这条赛道所有人的问题。

**⑤ 测量轮周期 ≈1 µs——不用外部知识，能从论文自己反推：**
48.5 ns/轮被描述为"比测量率快 20 倍以上" ⇒ 测量率 ≈ **0.97 µs**；再看 d=51 的 543.9 ns（达标）
与 1064 ns（不达标）——**两处都指向 ≈1 µs**。

**⇒ 于是真正的硬约束是"`ns/轮 ≤ ≈1 µs`"，不是"追上 Helios 的 11.5 ns"。**

| | 器件 | LUT | ns/轮 | 相对 ≈1 µs |
|---|---|---|---|---|
| Helios d=21（无虚拟化，4,620 PE） | VCU129 | **898,715（实测）** | **11.5** | ≈87× |
| Helios d=27（4 虚拟 PE） | VCU129 | — | 48.5 | ≈20× |
| Helios d=51（重度虚拟化） | VCU129 | 796,000 / 85 MHz | 543.9 | ≈1.8× |
| Helios d=51 @ p=0.005 | VCU129 | 796,000 | 1,064 | **0.94× ✗** |
| **本项目 d21 / n=7 / J=1**（推荐，D11） | **VU9P 1.18M** | **≈687K（58%，外推）** | **≈582–605**（P0b 实测斜率） | **≈1.6–1.7× ✓** |
| 本项目 d21 / n=7 / **J=3**（原 D10，已废） | VU9P | ≈230K（20%，粗算） | **≈1,750–1,815**（实测斜率 ×3） | **✗ 破线（实测口径）** |

**⇒ "能不能单卡做大 d" 的答案是"能"**：我们 d21/n=7 的**外推**面积比 Helios **实测**的 d21 还小
（687K vs 899K），代价是 ns/轮 慢 ~30–40×，但**仍在 ≈1 µs 以内 —— 前提是时钟收敛到 ≈6.5–7 ns**；
若只到现有最大配置（`surface d5 n=2`）的 **10.6 ns**，就是 **≈0.95–0.99 µs/轮，贴着线**（报告 §6.25）。
真正会破线的是 J=3 那一行——**这就是推翻 D10 的全部理由**（P0b 已把它从"按外推"升级为"按实测"）。

**⑥ 两条要顺手记住的：**
- **Helios d=21 的状态也是 FF 形态**：论文原文 "**We implement all shared memories as FPGA
  registers, i.e., `reg` in Verilog.**" ⇒ **FF 形态不是 d21 的障碍**。设计文档 §6.1 那句
  "LUTRAM 是 d21 的必需项"应改读为"**LUTRAM 是'把 d21 塞进 < ~900K LUT 的器件'或'做 d>21'
  的必需项**"。
- **每节点面积是同一量级**（报告 §2 已核对口径）：Helios d21 = 898,715 / 4,620 PE =
  **194.5 LUT/PE**（正文 200），我们 **182 LUT/节点**。从前那句"2 倍差距"是分母口径错误。

**⑦ ✅ 这张表里唯一没有实测支撑的环节，已在 2026-09-20 补上（P0b，报告 §6.25）：**
- `n = 2/3/5` @ d3 与 d5（rep 与 surface 各一套，**10 个配置全 PASS**）实测：
  **`每轮拍数 = 2 + n·S(d)`，残差 0 拍**；`S(3) = 11.833`、`S(5) = 12.333`。
- **交叉验证**：`S(d)` 被**扁平阵列的 stage 普查**（`cycles.csv`，完全独立的测量）按
  `S = S_nomerge + 2·S_merge` 预测到 **±0.00%** —— 也就是说**两趟 merging 的 ×2 是真的**，
  而上表原来那行 `≈355–445 ns/轮` 恰好漏掉了它（反推回去是每片 7.8–9.8 拍 = **单趟**的 stage 数）。
- ⇒ 本表两行已按实测更新为 **≈582–605 ns/轮（余量 1.6–1.7×）** 与
  **≈1,750–1,815 ns/轮（J=3，破线）**。
- 唯一剩下的外推项是 `S_merge(21)`（取 4.75–5.00 的饱和值）；**斜率、截距、两趟 ×2 都是实测**。
- 补测前唯一的实测锚点 **d7 平面 2:1 = 7.75 拍/轮 = 88.7 ns/轮 @87.4 MHz**，
  与 `2 + S_单趟(d7) = 9.75` 同量级一致。
- 顺带记一条**别搞混**的：`cycles.csv` 里的 `1:1` / `2:1` 是**成长调度**（`ONE_ONE` 参数：
  0 = 2:1 = Snowflake，1 = 1:1 = 基线），**不是"每 PE 几个节点"**。那张表量的是调度代价，
  以及 MINTS 的 `split_factor`（1.54–1.63）；**它不是复用因子的数据。**

**频率**：7 系列比 UltraScale+ 慢，而且 **D1 的 6.5 ns 是给 VU9P 定的**。
小配置（rep d3 780 LUT / surface d3 3.2K LUT）只占芯片百分之几，布线短，预计
**rep d3 ≈5–6 ns、surface d3 ≈7–9 ns、surface d5 ≈12–15 ns**（**估计值，未实测**）。
⇒ **上板前必须用真器件重跑一次综合**（`sweep.ps1 -Part xc7z020clg484-1 -Mode synth`），
按实测重新声明约束；`WNS ≥ 0` 的底线不变。

**PS 是白送的系统外壳**：syndrome 注入 / correction 回读 / golden 比对都可以由 A9 + DDR 做，
正好补上 §3.6C 那个"上板最大的缺口"，而且比 Helios 的 MicroBlaze + AXI 通路简单。

#### 3.8 噪声模型：唯象 vs 电路级（**Snowflake 原文是电路级**；**D14 已采纳："加一列"不替换**）

**先把事实查清（都在仓库里，可复核）**：

| 事实 | 出处 |
|---|---|
| **Snowflake 论文用的是电路级噪声** | `snowflake.pdf` 摘要："for the surface code **under circuit-level noise**, is roughly 25% more accurate than the Union–Find decoder"；Appendix A 描述电路级模型 |
| **Snowflake 用的是 unrotated surface code** | 同文 Fig. 7："the distance-5 **unrotated** surface code" |
| **我们的 golden 是唯象（硬编码）** | `snowflake_sim/ref/gen_golden.py`：`(Repetition if … else Surface)(a.d, "phenomenological", scheme="frugal")` |
| **localuf 两种都实现了** | `localuf/type_aliases.py`：`NoiseModel = Literal['code capacity','phenomenological','circuit-level']`，另有只对电路级生效的 `Parametrization`（standard / balanced / ion trap） |
| **Helios 论文两列都报** | Table 1 有 phenomenological 与 circuit-level 两列；电路级 **d=21 = n/a（装不下）** |

**电路级的代价——本轮实测（直接跑 localuf，同一 `scheme='frugal'`）**：

| d | 唯象 NN / NE | 电路级 NN / NE | 边数倍率 | **最大节点度数** |
|---|---|---|---|---|
| 3 | 36 / 51 | 36 / **69** | ×1.35 | 6 → **10** |
| 5 | 150 / 285 | 150 / **457** | ×1.60 | 6 → **12** |
| 7 | 392 / 847 | 392 / **1,453** | ×1.72 | 6 → **12** |

**关键洞察（这条决定了工作量）**：**节点数完全不变，只是边变多、度数变大**；
而我们的 PE 本来就是 **`NDIR = 12` 的方向结构**（唯象只用满 6 个方向 —— 这正是
`--dirs used` 只能砍掉 6 个的原因），**电路级恰好用满 12 个**。
⇒ **RTL 结构不用改**：这是一次"**表重新生成 + 重新回归**"，不是架构改动。

**代价估计**（诚实标注为估计，机理清楚）：
- 边模块：占全局 6%（d7 实测），数量 ×1.7 ⇒ **+4–5%**；
- PE 的 12 方向 argmin 由"6 路活"变"12 路活"⇒ 合并通路 ≈ ×2 ⇒ **整体 +50–65%**；
  与 Helios 的 LUT/PE 倍率（1.6–2.0×）**两条独立路径一致**。
- 落到具体配置：d3 4,091 → ≈6.5K；**d5 23,168 → ≈35–38K（Z-7020 的 66–72%，紧但可行）**；
  **d21/n=7 687K → ≈1.0–1.15M，逼近甚至超过 VU9P 的 1.18M**（那时才轮到 LUTRAM 或 n=9）。

**对写文章、对 Helios 的好处（按重要性排）**：

1. **同口径**：Helios Table 1 有两列，我们现在只能对唯象列；改了两列都能对。
2. **可能拿到 Helios 拿不出的结论**：**Helios 电路级 d=21 是 n/a**。如果我们在**同一等级器件**
   （VU9P，必要时 n=9 或 LUTRAM）上做出**电路级 d=21**，那就是一条他们做不到的结果 ——
   比"唯象 d21 面积比他们小"强得多。
3. **审稿口径**：2025+ 的 QEC 解码器论文默认电路级，只报唯象会被要求补。
4. ⚠️ **但应该是"加一列"，不是"替换"**：唯象那一列是我们现有的**全部实测资产**
   （10 条 lattice 回归 + 9 条门级回归 + 全部面积/时序），删掉等于把这些验证投资作废。
   正确做法：**唯象 = 已验证基线，电路级 = 新增一列**。

**建议的落地顺序（便宜 → 贵，每步都要过逐行回归）**
（**2026-09-21 已按 D16 重排：下面第 1–2 步 = §4 的 P0″（✅ 已完成，见 §2.12 / 报告 §6.29），
第 3–4 步 = §4 的 P2，且都排在 rotated 之后**）

1. ✅ `gen_golden.py` 与 `generate_snowflake.py`/`make_lattice_sim.py` 各加了 `--noise`
   （默认 `phenomenological` ⇒ **默认路径逐字节不变**，已验证：三份唯象表 + 两份 golden 同哈希）；
   **加断言 `max degree ≤ NDIR`**（✓ 已加，**实测 d5/d7 正好 = 12，零余量**）；
   **并且验了"生成器的三条几何前提在电路级图上是否成立"** —— **结论：不成立，已修**
   （边类 3 类 → `(Δlayer, Δrank)` 完整类；d3/d5/d7 原本有 10/76/246 个 cell 冲突）。
   ⚠️ **`rep` 没有电路级**（localuf `NotImplementedError`）⇒ **回归载体只能是 surface**。
2. **先做 d3 电路级**（**用 surface d3，不是 rep**）：RTL 回归 +（门级回归）⇒
   若 PASS，说明"表生成 → RTL → 网表"整条链路对电路级是通的；
3. **再做 d5 电路级** + 一次真器件综合 ⇒ 面积/频率落到实测；
4. 只有 1–3 都通过，才谈 d21 电路级的外推。
   **⚠️ 但这一切都排在 P4（rotated）之后**（D16）：先用检查器把 rotated 图过一遍两种噪声。

**风险（必须一起记）**：
- ⚠️ **电路级的最大度数正好 = 12 = `NDIR`，没有余量**：换 `Parametrization`
  （ion trap / balanced）可能产生 >12 的度数 ⇒ 那才是结构性改动。
  **应把"`max degree ≤ NDIR`"做成生成器断言**（现在的断言里没有这一条）。
- 电路级的时间方向更长，窗口/缓冲参数（`2⌊d/2⌋`）要与 Snowflake 的电路级设置对齐；
- 回归基线要重建（现有 golden 全是唯象），新增一列**不能覆盖**旧的。

#### 3.9 为什么"同样的 d，我们的物理量子比特更多"：**rotated vs unrotated**

**根因是码型，不是实现**：

| | 码型 | 物理量子比特 @ d=21 | 解码图节点（= 我们要实现的 PE/节点数） |
|---|---|---|---|
| **Helios** | **rotated** surface code | 论文原话 "a distance d **rotated** surface code is a topological code made out of **2d²−1 physical qubits**" ⇒ **881**（441 数据 + 440 辅助） | 论文原话 "(d+1) × ((d−1)/2) × d vertices" ⇒ **4,620** |
| **本项目**（Snowflake/localuf） | **unrotated** surface code | `localuf/codes.py`：`DATA_QUBIT_COUNT = d² + (d−1)²` ⇒ **841 数据 + 840 辅助 = 1,681** | 每层 `d(d+1) = 462` × `d = 21` 层 ⇒ **9,702** |
| **比值** | | **1.91×** | **2.10×** |

（d=3 也对得上：unrotated 13 个数据比特 vs rotated 9 个，1.44×；d→∞ 时趋近 2×。）

**对论文对比的三条含义（重要）**：

1. **"同 d 比总量"不是同类比较**：分母是两种码。报告 §2.4/§6.9 用的
   **"每节点成本"（我们 182 LUT/节点 vs Helios 194.5 LUT/PE）**才是公平口径，那条结论仍然成立；
   但**任何"总规模/总面积"的对比都必须注明码型差异**。
2. **这给出一个 ≈2× 的算法侧杠杆**：若改用 rotated 码的图，同 d 下节点/边数直接减半
   ⇒ d21 从 687K LUT 变 ≈350K。**这比 RTL 侧剩下的任何杠杆（LUTRAM / MINTS / 布局）都大。**
   代价：**localuf 不支持 rotated**（要自己写参考实现或改 localuf），而且那等于换一个算法问题
   ⇒ **这是算法侧的决定，不是 RTL 的决定**，且必须先有独立的 golden 才能谈。
3. **Helios 的 100 MHz/11.5 ns 也是 rotated 码的代价**：他们的 PE 数少一半，
   但每个 PE 要处理 6 邻居；我们的 unrotated 图每层更宽。**两个设计各自站在自己码型上，都是"每节点 ~180–195 LUT"。**

## 5. 红线

- 任何 RTL / 生成器改动**必须**通过逐行回归才能计入结论；**默认路径必须逐字节不变**
  （跑一次无 `-Defs` 的回归比对轨迹）。
- 新开关一律 `ifdef` 且默认关闭。
- 报告里的数字必须来自实测；**负结果同样要写进去**（已有 13 例：MINTREE、pblock、`--dirs used`、
  posedge-Q seam 负对照、MINTS 的面积假设、MINTS 单 bank 变体、MINTS+BUSYREG 的 d7 达标外推、
  LATTICE 第 (a) 步的"零成本"预测、**lattice n=2 的"面积下降"预期（本轮）**、
  **surface d5 的 754 LUT 假结果（本轮）**、**d5 lattice 的 elaborator 栈溢出（本轮）**、
  **LUTRAM 推断结构性不可行（本轮）**、**"七种读侧变体"整组结论被推翻（本轮）**）。
- **不要让"PASS"变成空判**：新激励先看计数器是否非零；能构造负对照就构造
  （§2.3 的 6/6 FAIL 是整个 seam 结论的地基）。**同样不要让"断言"变成空判**（§1 的 dict 陷阱）。
- 组合/映射表**必须由 localuf 算出**，不能手填（§2.7 的 ptrmap）。
- **小 d 的相对收益不能外推到大 d**：SERIAL 比 SLICED 快 19.8%（d3）但只 1.2%（d5）。
- **一种形态的面积数字不能外推到另一种形态**：FF 型 ≠ RAM 型；n=2 ≠ n=7；
  bbox 上界槽位 ≠ 紧致槽位。
- **文档一律用显式 UTF-8 的 python IO 读写**，不要用 PowerShell `Get-Content`/`Set-Content`（§1）。
- 生成器改动后要验证默认路径不变（`--slices` 不改 `.svh`，已实测）。
