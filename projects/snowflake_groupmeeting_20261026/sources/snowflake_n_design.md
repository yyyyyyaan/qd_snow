# Snowflake-n 设计：把窗口沿时间轴切分、分时复用一个 lattice

> 目标：在**单颗 FPGA**（不引入多 FPGA）上做到 d=21 甚至更大。
> 本文件只讲设计与依据，实测数字全部来自本仓库（VU9P，Vivado 2020.2，布线后）。
> 依赖的既有结论见 `optimization_report.md` §6.4（面积/频率律）、§6.10/6.11（CS 与 LUTRAM）、§6.12（拥塞来源）。

> **"单卡做大 d 到底行不行"——对照 Helios 的实测口径（2026-09-20，D11，详见
> `NEXT_SESSION_PROMPT.md` §3.4b）**：
>
> | | 器件 | LUT | ns/轮 | 相对测量率(≈1 µs) |
> |---|---|---|---|---|
> | Helios d=21（**不用**虚拟化，4,620 PE 全并行） | VCU129 | **898,715（Table 1 实测）** | **11.5** | ≈87× |
> | Helios d=27（4 虚拟 PE/物理 PE） | VCU129 | — | 48.5 | ≈20× |
> | Helios d=51（重度虚拟化） | VCU129 | 796,000 / 85 MHz | 543.9 | ≈1.8× |
> | Helios d=51 @ p=0.005 | VCU129 | 796,000 | 1,064 | **✗ 不达标** |
> | **本设计 d21 / n=7（J=1，FF 形态）** | **VU9P 1.18M** | **≈687K（58%，外推）** | **≈582–605**（P0b 实测斜率外推） | **≈1.6–1.7× ✓** |
> | 本设计 d21 / n=7 / J=3（原方案，**已废**） | VU9P | ≈230K（粗算） | **≈1,750–1,815**（实测斜率 ×3） | **✗ 破线（实测口径）** |

> 三条结论：
> 1. **能单卡做大 d**：我们的 d21/n=7 外推面积比 Helios **实测**的 d21 还小（687K vs 899K），
>    代价是 ns/轮 慢 ~30–40×，但**仍在 ≈1 µs 的测量轮周期以内**。
> 2. **"越复用越慢"不是本设计独有的缺陷**：Helios 从 d≥27 起做的是同一件事
>    （"mapping multiple virtual PEs to a single physical PE"），代价也近似线性，
>    且它 **d=51 在 p=0.005 时同样不达标**。他们的面积按 **O(d³)** 长（论文原话）。
> 3. **LUTRAM 不是 d21/VU9P 的必需项**（Helios d21 本身就是 FF 形态）；它只在
>    "要塞进 < ~900K LUT 的器件"或"做 d>21"时才必需。
>
> ✅ **这个环节已经补上了（2026-09-20 · P0b，报告 §6.25）**：`n` 轴的实测点现在是
> **n=2/3/5 @ d3 与 d5**（10 个配置全部逐行 PASS），拟合 `每轮拍数 = 2 + n·S(d)`
> **残差 0 拍**；`S(3)=11.833`、`S(5)=12.333`，并且被**扁平阵列的 stage 普查**
> `S = S_nomerge + 2·S_merge` 独立预测到 **±0.00%**。
> ⇒ **`≈355–445 ns/轮` 作废，改为 `≈582–605 ns/轮`（d21/n=7，@6.5 ns）**，余量 **≈1.6–1.7×**；
> **`J=3` 是 ≈1.75–1.8 µs/轮，明确破线**（实测口径）。**口径修正的原因**：原外推漏掉了
> **两趟 merging 对 merging stage 的 ×2**（§6.25.2）。

> **⚠️ 上表的"面积估计"列是初版估算，只缩放了组合逻辑。§6.1 用实测的 NCTX 构建标定后
> 修正为：状态不随 lattice 缩小，`NSLOT × n` 份 context 状态 + 每节点每 context 的读写选择

> ⇒ **LUTRAM 化 context 状态（§6.11 判据 NCTX ≥ 8）不是可选优化，是打穿这个下限的唯一手段。**

> 修正后（`crosscheck_layers.py`：svh 表与 localuf 直接遍历**两种方法逐层一致**）：

`check_lattice_embedding.py surface 7` 的实测（直接走 localuf，不经打包向量）：

| 结构 | 实测 | 结论 |
|---|---|---|
| 每层节点数 | 56 × 7 层，**完全相同** | ✓ 同构前提 |
| 层内邻接 | 4 种空间偏移 `(0,±1) (±1,0)`，**每层计数完全相同**（49/49/36/36） | ✓ **层内拓扑逐层一致** |
| 层内度分布 | 每层都是 `1:14, 3:12, 4:30` | ✓ 一致 |
| 层间（垂直） | 偏移只有 `(t±1, 同空间位置)`，每方向 42 条 | ✓ 规则 |
| 层间差异 | **只出现在窗口两端**：底层只有 `+1`（42），顶层只有 `-1`（42），中间层两个方向各 42 | **3 种端口签名**（底/中/顶） |

这与 Helios-n 的成立前提（"每个 PE 有固定边数、连到相邻 PE，因此所有子图都能映射到同一 lattice"）
**完全吻合**，是本次设计最重要的正面结论；一个层组的内部是完全规则的，
只有组的两个端面需要"对外接口"（由 §4 的 seam 提供）。

## 2. lattice 与子图

**定义**（与 Helios-n 一致，术语对齐论文）：

- **子图（sub-graph）**：连续 g 个时间层上的节点集合，加上**所有至少一端落在其中的边**。
- **lattice**：一份硬件实现，拓扑与子图相同、规模 ≥ 最大子图。所有子图都能映射到它。
- **n**：片数，`n = ceil(nl / g)`（`nl` = 窗口层数，d=21 时 21）。`Helios-n` 里的 n 就是这个。

**lattice 的规模** = 最大子图的（节点数，触及边数）。
面积估计用 §1.1 的模型：`LUT_lattice ≈ 86 × 触及边数`，全部参数见 §6。

**为什么 lattice 必须包含"触及边"而不只是内部边**：每条边在我们实现里是一个独立模块
（`snowflake_edge`），它必须被实例化才能被求值；跨片边的另一端在别的 context 里，
所以它的状态由 §3 的"缝"提供。

## 3. 映射机制

### 3.1 现状：PE 的"我是谁"是编译期常量

现在每个 PE 的身份、邻居表、方向表全部来自生成的常量向量
（`SNOW_NB_VEC` / `SNOW_REV_VEC` / `SNOW_SYNIDX_VEC` …），**不可在运行期改变**。
snowflake-n 要求把它变成"运行期可按 context 索引"。

### 3.2 关键约束：**逻辑 ID 不能被重排**（frugal 簇号编码是按 ID 阈值定义的）

逻辑 ID 来自 localuf，而且**必须保持**：Snowflake 的 frugal 簇号编码由 `SNOW_CID_DELTA(a0)` 给出，其 `limit/small/big` 是按 **ID 阈值**定义的（`generate_snowflake.py:59` 的 `id_below` 公式）。所以不能靠"重排 ID 让每层连续"来简化映射——那会改变定根行为，直接破坏与 localuf 的逐行一致性。

**两个候选方案，其中第一个已被否决**：

- ~~**方案 R：在生成器里按 `(层, 层内位置)` 重排节点 ID。**~~
  **否决理由（已核实）**：Snowflake 的 frugal 簇号编码**按节点 ID 阈值定义**
  —— 生成的是 `SNOW_CID_DELTA(a0) = (a0 >= limit) ? big : small`，
  而 `limit/small/big` 来自 localuf 的 `id_below` 公式（`generate_snowflake.py:59`）。
  重排 ID 会改变每个节点的 delta 规则 → 改变定根行为 → **与 localuf 的逐行黄金对比直接失效**，
  而"逐行等于 localuf"正是本项目的正确性定义。所以**逻辑 ID 必须保持 localuf 的编号**。

- **方案 T（采用）：保留逻辑 ID，lattice 槽位用显式映射表。**
  lattice 里每个物理槽位只持有"它当前服务的逻辑节点"的**状态值**（`cid`/`ptr`/标志位，
  这些值本身就引用逻辑 ID，不需要翻译）；需要显式给出的只是**常量类信息**：

  | 需要的表 | 内容 | d21 (g=3, n=7) 规模 | 说明 |
  |---|---|---|---|
  | 槽位 → 逻辑 ID | reset 时 `cid <= ID[slot]` 用 | 1,386 × 10 bit **× n** ≈ 97 Kbit ≈ 1.5K LUTRAM | 只在 reset 时读，可用 ROM 一次装载 |
  | 槽位端口掩码 | `is_bnd/is_top/is_bot/has_above` + 该方向的邻居槽位 | 1,386 × (4 + NDIR×PTR_W) ≈ 1,386 × 52 ≈ 72 Kbit | 与 context 无关时**只需一份** |
  | 邻居槽位偏移 | 方向 d 指向哪个槽位 | 随掩码一起 | 与 context 无关时只需一份 |
  | `syn_idx` | 该槽位取 syndrome 的哪一位 | 1,386 × log2(NSYN) | 与 context 无关时只需一份 |

  关键点：**掩码/邻居偏移/syn_idx 只与"层模式"有关，与 context 无关**——
  d21 的 21 层按模式只需少数几种（§1.4 显示周期 3），所以这些表按"模式"存几份即可，
  面积可忽略；只有 reset ID 表需要每 context 一份。

### 3.3 lattice 可嵌入性：**已验证通过**（§1.4）

Helios-n 成立的前提是"所有子图都能映射到同一 lattice"（原文：每个 PE 有固定边数、连到相邻 PE）。
这条现在对我们也有实测答案：

> **层内**：4 个固定网格偏移，7 层完全一致 → 一套层内接线服务所有层 ✓
> **层间**：`(t±1, 同位置)`，中间层双向各 42 条；**只有窗口底层缺 down、顶层缺 up** ✓
> ⇒ 一个规则 3D 网格 lattice + **只在两端生效的掩码**即可容纳所有层组。

层组（g 层一片）的端面就是 seam 的接口位置（每端 42 条垂直边 × 每边 3 bit 状态）。
`check_lattice_embedding.py` 输出的"3 种端口签名（底/中/顶）"就是掩码的全部内容 ✓
**所以 §3.3 的前置条件已满足**，不需要为"层间不同构"额外付代价。

#### 3.3.1 更强的复核（`fpga_flow/check_lattice_geometry.py`，**5/5 配置 PASS**）

上面那版是"计数一致"级别的证据。共享 lattice 的真正要求更强：**邻居路由必须是编译期常量槽位偏移**
——否则每槽位要一张 ~350 bit 的每 context 路由 ROM，d21/n=7 约 1.45M LUT，**超过整颗器件**（§6.1）。
新脚本直接走 localuf（不经打包向量，避开 §1.4 那个倒序解析坑），逐节点逐方向核对三件事：

| 检查 | surface d3 / d5 / d7 / d21 | rep d3 |
|---|---|---|
| **偏移常量性**：每个方向 `neighbour − self` 的索引差在全图**唯一** | ✅ 全部 | ✅ |
| **层同构**：每个时间层的**空间坐标集合完全相等**（不只是计数相等） | ✅ 全部 | ✅ |
| **面内端口可推导**：同一空间位置在不同层，N/S/E/W 的"有无邻居"是否一致 | ✅ 全部 | ✅ |

实测到的偏移（surface 码，索引 `(x, y, t)`，时间轴 = 2）：

```
N=(-1,0,0)  S=(+1,0,0)  E=(0,+1,0)  W=(0,-1,0)  D=(0,0,-1)  U=(0,0,+1)
```

即**解码图就是一个精确的 3D 网格**，d3 到 d21 全部如此（rep 码是 2D：`E=(1,0) W=(-1,0)
D=(0,-1) U=(0,+1)`）。三条推论直接决定 lattice 的实现形态：

1. **路由零成本**：槽位号取 `slot = t_local × plane_size + spatial_rank`，
   方向 d 的邻居就是 `slot + OFFSET(d)`，`OFFSET` 是 elaboration 期常量 ⇒
   **不需要任何路由 ROM**，§6.1 里那个 1.45M LUT 的最坏情况被排除。
2. **面内端口只与槽位有关**：N/S/E/W 的"有无邻居"由"是否越出 lattice"决定，是几何量 ⇒
   每槽位一个常量掩码，**与 context 无关**。
3. **只有 D/U 两个时间方向需要每 context 一位**（相邻层是否在本片内）
   ⇒ 每 context ROM 缩到 §6.1 算的 ~19 bit/槽位（逻辑 ID + IS_TOP/IS_BOT + 垂直 seam 选择）。

顺带用同一脚本核出了各配置的 **NSLOT 与共享倍率**（与 §6 的表一致）：
surface d3/n=2 → NSLOT 24（1.50×）、d5/n=2 → 90（1.67×）、d7/n=3 → 168（2.33×）、
**d21/n=7 → 1,386（7.00×，切片完全均衡）**、rep d3/n=2 → 8（1.50×）。

复现：`python fpga_flow/check_lattice_geometry.py`（或 `<code> <d> [n]` 单跑一个配置）。

#### 3.3.2 槽位编号方案：**已验证，零浪费**（`fpga_flow/check_lattice_slots.py`，5/5 PASS）

§3.3.1 证明的是"在 localuf 自己的索引空间里是网格"。RTL 需要的是更强的东西：
**一套所有片共用的槽位编号，使每个邻居都落在常量槽位偏移上。** 方案是层内 bounding box 的行主序：

```
slot(node) = t_local × P + (x − x_min) × NY + (y − y_min)
P = NX × NY     （每层槽位数）      t_local = 该层在**本片内**的序号（0 起）
⇒  N = −NY   S = +NY   E = +1   W = −1   D = −P   U = +P      （全部为编译期常量）
```

（rep 码是 2D：取 NX=1，只有 `E=+1 W=−1 D=−P U=+P`。）

实测（脚本逐节点逐方向核对"实际槽位差"与上式的预测值，**完全一致**）：

| 配置 | box | P | g_max | **NSLOT** | 最大片节点 | **空槽（浪费）** | 实测槽位偏移 | 跨片端口 |
|---|---|---|---|---|---|---|---|---|
| surface d3, n=2 | 3×4 | 12 | 2 | **24** | 24 | **0** | N=−4 S=+4 E=+1 W=−1 D=−12 U=+12 | 12 |
| surface d5, n=2 | 5×6 | 30 | 3 | **90** | 90 | **0** | N=−6 S=+6 E=+1 W=−1 D=−30 U=+30 | 40 |
| surface d7, n=3 | 7×8 | 56 | 3 | **168** | 168 | **0** | N=−8 S=+8 E=+1 W=−1 D=−56 U=+56 | 168 |
| surface d21, n=7 | 21×22 | 462 | 3 | **1,386** | 1,386 | **0** | N=−22 S=+22 E=+1 W=−1 D=−462 U=+462 | 5,040 |
| rep d3, n=2 | 1×4 | 4 | 2 | **8** | 8 | **0** | E=+1 W=−1 D=−4 U=+4 | 4 |

两条重要结论：

1. **每层的空间坐标集合恰好是一个完整矩形**（`spatial_n == P`，5/5 成立）
   ⇒ bounding box 里没有"洞"，**NSLOT 恰好等于最大片的节点数，零浪费**。
   这正面确认了 §6.1 面积模型用的 `NSLOT = max(片节点数)`——之前那只是个假设。
2. **路由表彻底不需要了**：六个方向就是六个常量整数，写进 `localparam` 即可。
   §6.1 里那个"1.45M LUT 路由 ROM"的最坏情况不只是被排除，而是**连表都不用生成**。
   每 context 只剩 §6.1 算的 ~19 bit/槽位（逻辑 ID + IS_TOP/IS_BOT + 垂直 seam 选择）。

**边界怎么处理**：面内方向"有没有邻居"= `slot + OFFSET` 是否越出本层的 box
（纯几何、每槽位常量掩码）；垂直方向 D/U 则要看相邻层**是否在本片内**
（每 context 一位）——不在片内就走 seam，seam 条目按 §6.1 的约定用**几何编址**
（第 k 个边界槽位 ↔ 第 k 个 seam 条目），于是 seam 索引也退化成常量。

复现：`python fpga_flow/check_lattice_slots.py [code d [n]]`。

## 4. 缝（seam）：跨片簇怎么处理

**问题**：Union-Find 的簇可以横跨整条时间轴，一个簇的树可能同时落在两个片里；
而另一片的 PE 状态此刻并没有加载到数据通路上。

### 4.1 先把依赖关系核对清楚（已对照 RTL）

沿时间轴切片会切断两类连线，**没有第三类**：

1. **跨层状态** `ab_*`（`snowflake_pe` 的 `ab_cid/ab_active/ab_whole/ab_defect/ab_ptr`）
   —— 来自"上一层那个节点"的**寄存器**；
2. **跨层边**：`e_grown`（边状态）以及经由边传递的邻居端口
   `nb_cid/nb_active/nb_grown/nb_push`。

关键性质（`snowflake_pe_array.sv` 逐条核对）：

- `nb_cid / nb_active / nb_grown` 直接接邻居 PE 的**寄存器输出** ⇒ 步内不会变；
- 唯一的**组合**端口 `nb_push` 来自邻居的 `o_push`，而 `push` 只依赖该 PE **自己的**
  `defect / n_ptr / IS_BND`（`det_def && n_ptr != PTR_C` 时 `push[n_ptr-1]=1`），
  **不依赖它自己的邻居** ⇒ **阵列内部不存在跨 PE 的组合链**。

⇒ 于是：**整个阵列的每一步都是纯 Jacobi 步**（每个 PE 只用"步开始时"的状态算下一步）。
这条性质是 seam 方案成立的根基，也是这轮把它写清楚的意义——原先只写了"每阶段同步"，
那是**不够**的。

### 4.2 seam 协议（精确版）：**每步一次的双缓冲快照**

- **内容**：边界层的节点状态（cid/active/whole/defect/grown/unrooted/busy/ptr ≈ 22 bit/节点）
  ＋ 跨层边的状态（growth 2 bit + ecorr 1 bit）。
  d21 g=3：`462 × 22 + 2,520 × 3 ≈ 17.8 Kbit ≈ 280 个 LUTRAM LUT`（面积可忽略）。
- **时序**（乒乓缓冲，保证 Jacobi 语义）：
  - 第 k 步内，先执行的片从 `seam_prev` 读片外邻居的**第 k−1 步**状态，把本片新状态写入 `seam_next`；
  - 后执行的片**同样**从 `seam_prev` 读（所以它看不到前一片在本步的新值 ⇒ Jacobi ✓），也写 `seam_next`；
  - 步结束时 `seam_prev ← seam_next`（一次缓冲切换，1–2 拍）。
- **正确性论证**：由 4.1，"片外状态"只通过 `ab_*` 与跨层边进入本片；seam 恰好携带这两类信息的
  **步起始快照**，因此本片的计算结果与"整窗执行时该片的结果"逐位相同；
  跨片的簇通过跨层边在**每步**交换状态，指针沿簇树逐步传播——正是整窗版的传播顺序。

**所以"跨片簇"不需要 halo/重叠层**（方案 B 可以放弃）：
seam 携带边界节点的完整状态，簇跨片只是"传播多花几步"，
而每个全局步内所有片都在做同一层迭代。

### 4.3 代价

| 项 | 代价 |
|---|---|
| 面积 | seam ≈ 280 LUTRAM LUT + 乒乓切换逻辑（d21 g=3），可忽略 |
| 每步拍数 | 每步要跑 **n 次片执行**（各片串行）⇒ **延迟 ∝ n**（这是 CS/Helios-n 的固有代价，已在 §6 量化） |
| 每次切换 | 1–2 拍缓冲切换（论文实测的每阶段 +2 拍同量级） |
| 验证 | 见 §7：n=2 逐行比对是 Go/No-Go 关口 |

### 4.5 seam 的内容、归属与重算规则（n=2 原型可直接照此实现）

**切片切断了什么（逐条对照 RTL）**：

| 被切断的东西 | RTL 出处 | seam 里怎么补 |
|---|---|---|
| 跨层**节点**状态 | `ab_cid/ab_active/ab_whole/ab_defect/ab_ptr` ← `pe_cid[AB_S]` 等（寄存器） | 边界层节点状态（cid + 7 个标志位 + ptr ≈ **22 bit/节点**） |
| 跨层**边**状态 | `above_growth[1:0]` / `above_ecorr` ← `ed_growth[AB_S]` | 边界处跨层边的 `growth`+`ecorr`（**3 bit/边**） |
| 跨层边两端的**组合脉冲** | `u_pulse`/`v_pulse` ← `pe_pulse[U/V]` | **不必显式传**：可由状态重算（见下） |

**重算规则（省掉一半 seam 带宽，也避免跨片组合路径）**：

- `push[d]=1` ⟺ `!IS_BND && defect && (n_ptr != PTR_C) && d == n_ptr-1` ⇒ 只依赖 `defect/ptr` ✓
- `pulse=1` ⟺ `active && !whole && !grown`（`ST_GH` 分支）⇒ 只依赖 `active/whole/grown` ✓

⇒ seam 只存**状态**，接收侧用同样的组合逻辑重算 `push`/`pulse` 即可。

> **勘误（2026-09 实施时）**：`pulse` 的重算规则成立（只依赖自身寄存器）；
> 但 `push` 的"只依赖 defect/ptr"**不完整**——它用的是 `n_ptr`（本拍 flooding 的
> argmin 结果），而 argmin 读该节点**自己的邻居 cid**（其中就包括 seam 输入），
> 所以"接收侧从影子状态重算 push"需要复制整套 12 方向最小搜索（halo），
> 不划算。已实现的 n=2 原型改为：**negedge 寄存器直接采样源的 push 组合输出**
> （它从拍首稳定，因为其输入只有寄存器与 D-shadow），见 §4.7 勘误。

**归属规则（保证每个 seam 条目只有一个写者）**：

| 对象 | 归属 | 依据 |
|---|---|---|
| 节点 | 其所在层所属的那个片 | 每节点只属一片 ✓ |
| 片内边 | 两端所在片 | — |
| **跨层（垂直）边** | **其 U 端（低 ID 端点）所在层所属的片** | 与 flat 核"边状态存在低 ID 端点"一致 ✓ |
| 该跨层边的 `above`（下面那条边） | 由**下方片**拥有，上方片通过 seam 读 | `above_growth` 依赖 |

**带宽核算（d21 g=3，一个切面）**：`462 × 22 + 840 × 3 ≈ 12.7 Kbit`（n 片的多个切面可时序复用，
只需一份双缓冲）。

### 4.7 仍然存在的风险（诚实列出）

1. **调度器改造**：现在的控制器是"整窗一次执行"，要变成"每步内 n 次片执行 + 缓冲切换"，
   且 `busy/done` 语义要按片聚合（参考已验证的非抢占仲裁 + drain 机制）；
2. **seam 的写冲突**：两个片都会写边界状态（各自的 owner 部分），要保证写入不重叠
   （按"层→片"归属划分，边界层的每个节点只属于一个片 ✓）；
3. **验证成本**：n=2 原型的逐行比对必须覆盖"簇跨缝"的轮次——用本地 golden 构造
   跨缝簇的 syndrome 模式来强制覆盖（不能只靠随机数据碰运气）。

### 4.8 未解问题：**串行/分时协议下 `push` 无法只靠"状态快照"过缝**（n=2 原型暴露出来的）

§4.2 的乒乓协议说"seam 携带边界节点的完整状态，接收侧重算 `push`/`pulse`"。
n=2 原型（§4.6/4.7，已实测通过）证明：**同拍执行**下这套内容清单是够的，
但**分时（串行）执行**下有一个 §4.2 没有覆盖的时序问题，必须先解决再做面积共享。

**问题**：`push` 不是状态，而是**本步状态的函数**。单片阵列里，节点 n0 在周期 k 读到的
`nb_push` 是邻居 m 的组合输出 `F(Q_k(m), Q_k(m 的邻居))`——其中 `Q_k` 是**本步开始时**
的寄存器值。分时执行时，全局步 k = [片 0 相位的 1 拍] + [片 1 相位的 1 拍]：

- 片 0 在步 k 的相位里提交，需要 `F(Q_k(m), …)`；
- 而片 1 只在**步 k−1 的相位**里评估过自己的组合逻辑，那时它算出的是 `F(Q_{k−1})`；
- 把 `F` 的结果在片 1 相位末寄存进 seam，得到的是 `push_{k−1}`，**晚一步** ⇒
  缺陷迁移晚一步 ⇒ merging 拍数与逐行轨迹都会变（等价性论证失效）。

注意这不是"seam 内容不够"，而是**评估时机**问题：`F` 必须在"消费方的相位"里被求值，
而它的自变量（m 的下一状态）只在"生产方的相位"里出现。

**四个候选解（按代价排序，都还没实现）**：

| 方案 | 做法 | 代价 | 备注 |
|---|---|---|---|
| **B. 边界节点双评估** | 生产方相位里再复制一套 `push` 逻辑，喂**下一状态**（`o_n_*` 已有），相位末寄存 ⇒ seam 里就是 `push_k` | 边界节点的 merging 组合逻辑 ×2（d21 g=3 时边界≈33% 节点 ⇒ 全设计约 +20% 面积） | 语义精确、逐行可比；`pulse` 不需要（只依赖自身寄存器，可重算） |
| **C. halo + 消费侧重算** | seam 额外携带 m 的**同片邻居** cid/grown，消费侧复制 argmin | 每跨缝端口一套 12 方向比较器 + halo 带宽 | 面积最贵，且要逐位复刻 `break`/RESET quirk，风险高 |
| **A. 跨片组合直通** | `push` 不过寄存器，直接拉线到消费片 | 0 面积、0 额外拍 | **同拍原型正是靠它等价**（negedge 只是仿真里的重定时）；片内可行，**跨 FPGA 不可行**，且会拉长关键路径 |
| **D. 接受晚一步** | seam 存 `push_{k−1}` | 0 | 逐行等价失效；只能改用"不动点相同"的论证 + 端到端纠错率验证，**与本项目正确性定义冲突** |

**建议**：面积共享那一步先做 **B**（精确、可继续用逐行回归守），
并把"边界节点占比"作为选 g 的新约束（g 越大边界占比越低：d21 g=3 时 33%，
g=7 时 1/7≈14%）——这条会反过来影响 §6 的参数选择。
同拍原型（方案 A 的等价形式）保留为**语义参考实现**：任何分时版本都必须
在"每全局步一次 dump"的口径下与它逐行一致。

#### 4.8.1 更新（`SNOW_SERIAL` 实测后）：**廉价半已解决，B 只在共享 lattice 时才需要**

上面的分析里有一句隐含前提需要挑明：**"片 1 只在步 k−1 的相位里评估过自己的组合逻辑"**。
这句话**只对面积共享版本成立**（那时片 1 的状态根本不在触发器里，组合逻辑无从求值），
对**两实例集**的分时原型**不成立**——所有 NN 个 PE 都物理存在，
它们的组合输出在**每一拍都被求值**，只是提交被 `commit_en` 门控。

于是 §4.8 的问题分成两半，其中一半是免费的（已实现并逐行验证，见报告 §6.18）：

| 源相位 vs 消费相位 | 源的活线 | 方案 | 代价 |
|---|---|---|---|
| **晚**（源还没提交） | 就是 F(Q_k) | **方案 A 的精化：直连** | **0**（不插寄存器） |
| **早**（源已提交） | 已经变成 F(Q_{k+1})，错 | 在**源自己相位末**锁存 F(Q_k) | 1 个寄存器（**单缓冲**即可） |

要点：
1. 单缓冲够用，因为同一步内"写在先、读在后"，下一步开始前不会再写 ⇒
   **n=2 时每个组合跨缝点只需一个方向的寄存器**，比上表"方案 B"估的
   "边界节点 merging 逻辑 ×2"便宜得多（B 复制的是**逻辑**，这里复制的是**一位触发器**）。
2. 直连的那一半仍然会拉长关键路径（跨片组合），所以**跨 FPGA 时这半也要换成寄存器**——
   届时才是真的需要 B。单 FPGA 内部这半是免费的。
3. `pulse` 不需要任何处理：它只依赖节点自身寄存器（`pe_pulse` 是 `o_pulse` 的组合），
   与 §4.8 原判断一致。

**因此 §4.8 的"未解"状态改为**：

* ✅ **两实例集分时**（`SNOW_SLICED;SNOW_SERIAL`）：已解，6/6 逐行回归 PASS
  （rep d3 / surface d3 / surface d5 × std/seam 激励），拍数 = `NSLICE × live + idle`
  （实测 209 = 2×89+31、215 = 2×92+31）。**但不省面积**——它是协议验证，不是面积方案。
* ⬜ **共享 lattice 分时**（面积真正 ÷n 的那一步）：仍需 **B**。
  而且此时"消费方相位里求值生产方的 F"做不到（生产方状态不在触发器里），
  必须**在生产方相位内**用 `o_n_*` 次态喂一套复制的 merging 逻辑，相位末寄存。
  这会让边界节点多一套比较器 —— 但**报告 §6.17 的实测已经警告过**：
  在这个设计里"多一套比较器"的面积代价可能比想象的大（MINTS 两 bank 版 +24~35% LUT），
  所以 B 的面积账要**实测**，不能沿用 §4.8 的"+20%"估算。

另外 §4.8 没预料到的**第二个**串行协议坑（同样已修，报告 §6.18.2 ②）：
**任何"跨全阵列的组合归约"被全局控制器消费时，不能在 `phase_last` 取样**，
因为那时早相位片已经提交过了。`commit_bits`（所有 commit 边的 `ecorr` 向量）就是这样
出错的——状态行 2314/2314 全对、commit 却 0/6。修法是在**相位 0** 锁一份。
`any_step_busy` 是同一问题的另一实例（解法：本片报组合 `busy_c`、他片报本步已锁存的 `busy`）。
**共享 lattice 版本会把这类点放大多倍（每片一套归约），这条规则应当作 checklist。**

#### 4.8.2 更新（共享 lattice 实测后）：**已解，且完全不需要方案 B —— 相位不变性**

§4.8 的整个难度来自一个隐含假设：**消费方只能"取用"生产方在更早相位算出的结果**，
所以要么把它寄存下来（晚一步），要么在生产方相位里再算一套（B 的双份逻辑）。
共享 lattice 的实现证明这个假设不成立：**组合逻辑不是只能算一次**。
只要把每个 cell 的输入都做成"**本 stage 开始时**的值"，它在**任何相位**被求值都得到同一个数
——包括 `push`：`push = !is_bnd && defect && (ptr != C) && (d == ptr-1)`，
其中 `defect`/`ptr` 是状态，而 `ptr`（确切说是 merging 当拍算出的 `n_ptr`）本身也只是
**本 stage 状态**的组合函数。于是"生产方的 F"根本不需要被携带过缝：消费方在自己相位里
**重新求值**即可，结果逐位相同。

做法只有一条规则（报告 §6.21）：

```
每个端口读源 cell 的状态时，与"当前正在跑的相位"比较：
    源 slice <  phase   ->  读镜像（该 slice 本 stage 已提交，镜像里是 stage 首值）
    源 slice >= phase   ->  读寄存器（本 stage 尚未提交，寄存器就是 stage 首值）
```

关键是这个选择必须是**动态的**（与 `phase` 比较），不能是每条链路的编译期常量：
常量只在"消费方在自己的相位上被求值"时才对，而阵列的输出是**跨 cell** 被读的
（`push` 抽头、边的 `flip`/`pulse`），所以一个 cell 在相位 p 求值必须和在别的相位求值一样。

| 方案 | 是否需要 | 代价 |
|---|---|---|
| B. 边界节点双评估（复制 merging 逻辑） | **不需要** | 0 |
| C. halo + 消费侧重算（复制 argmin） | **不需要** | 0 |
| A. 跨片组合直通 | **就是它**（但不是"拉一根线"，而是"输入端相位不变"） | 每个端口 1 个小比较器（常量 slice vs `phase`）+ 地址 mux |
| D. 接受晚一步 | 不需要 | 0 |

修正 §4.8 的两条判断：

1. **"`F` 必须在生产方相位里被求值"是错的**：`F` 可以任意次、在任意相位重求，
   前提只是它的自变量必须是 stage 首值。原分析把这句写成了"自变量的下一状态"——
   `push` 要的不是源的次态，而是源**当拍**的组合量（`n_ptr`），而它是 stage 首值的函数。
2. **"A 会拉长关键路径"这一半仍然成立**（跨 slice 的组合路径在单 FPGA 内免费、
   跨 FPGA 时必须换寄存器）——这也是多 FPGA 仍未解的部分，但单 FPGA 目标下 A 就够了。

实测（报告 §6.21）：`push` 跨 slice 直连 + 动态 bank 选择后，六条逐行回归全 PASS，
`rep d3 / surface d3 / surface d5 × std/seam`。**没有为 `push` 增加任何寄存器或比较器逻辑**。

#### 4.8.3 更新（合并数据通路时必须回来解决 §4.8）：**两趟（two-pass）stage**

把"一个槽位 NCTX 个数据通路"合并成"一个槽位一个数据通路"时，§4.8 的问题**会重新出现**，
而且这次不能再用"直连活线"绕过。原因很具体：

扁平阵列里，节点 Y 在 merging 里收到的是邻居 X 的**组合输出** `push`
（`pe_nb_push[n][d] = pe_push[NBR][REV]`），而

    push(X, d) = !IS_BND(X) && defect(X) && (n_ptr(X) == d+1)

其中 `n_ptr(X)` 是 X **本 stage 的 flooding 结果**——它是 X 的*输出*，不是 X 的*状态*。
当前实现之所以免费拿到它，是因为**每个 (槽位, 切片) 都有自己的数据通路**：
X 的那份 datapath 一直存在，组合输出一直有效（报告 §6.20.9 已实测：这正是当前实现面积不降的原因）。

合并之后，X 的数据通路在别的相位正在算**另一个 context**，所以：

| X 的相位 vs 消费者 Y 的相位 | 合并前（每 context 一套 datapath） | 合并后（一槽位一套） |
|---|---|---|
| 相同（同一片） | 直连活线 | 直连活线 ✅ |
| X 的相位**早**（本 stage 已跑过） | 直连活线 | 在 X 自己相位末锁存（单缓冲）✅ |
| X 的相位**晚**（本 stage 还没跑） | 直连活线 | ❌ **拿不到本 stage 的 `n_ptr`** |

第三行就是 §4.8 的原问题。两条老出路都很贵：

- **方案 B/C（复制一份 flooding 逻辑）**：消费者要判断"X 的 argmin 是不是我"，
  就得读 X 的**全部**候选邻居的 cid 并做一次 12 路最小值搜索。
  §6.15 实测 **12 方向最小值搜索占全设计 61–64%**（d7 每节点 114 LUT）——
  按 d21/n=7 的 **5,040 个跨片端口**（§2.5 表）估算，这一项就是 **几十万 LUT 量级**，
  与整个 lattice 的估算（§6.1：≈687K）同阶。**基本可以判定不可行**
  （这是估算，若要下结论需要一次实测钉死）。
- **方案 D（接受晚一步）**：与本项目正确性定义冲突，不可用。

**真正可行的出路：把 merging 拆成两趟（每趟 NCTX 个相位）。**

    pass A：每个 context 只做 flooding —— 算 n_cid / n_ptr / n_grown / busy，并提交进 bank
    pass B：每个 context 只做 syncing —— 读**邻居在 bank 里已经更新好的 ptr**
            （以及自己刚提交的 ptr）来判断 push/flip、更新 defect/active

关键在于**`ptr` 本来就是状态字的一段**：pass A 提交之后，X 本 stage 的指针就躺在 bank 里，
pass B 只要把"X 是否指向我"变成一次**比较**（读 X 的字，比较它的 ptr 是否等于指回来的方向），
而这次读**已经存在**（当前 RTL 为了 cid/active/grown 已经在读同一个字）⇒ 几乎零额外面积。

语义等价性：扁平阵列的一拍里，flooding 与 syncing 用的是**同一份 start-of-stage 状态**
（`n_ptr` 与 `push` 都是它的组合函数），所以拆成两趟后 pass B 读到的 ptr 与扁平阵列同拍算出的
`n_ptr` 逐位相同 ✅。代价只有**延迟**：merging 从 NCTX 相位变成 2×NCTX 相位；
一个逻辑步原本 5 个 stage（D/G/M/g/m），其中 M 与 m 需要两趟 ⇒ 步长从约 5·NCTX 变成约 7·NCTX（+40%），
面积不增加。

**这一条同时解释了当前实现为什么"更大更慢"**：它用 datapath 复制换掉了两趟，
而 datapath 复制的代价（+15% LUT、FF 翻倍）比多两趟相位贵得多。

**待做**：按这个方案实现合并，并实测两趟带来的相位代价与面积收益。


#### 4.8.4 两趟 stage 的两个关键细节（推导，未实测）

要把 §4.8.3 的两趟方案落成 RTL，有两处**必须一开始就做对**，否则会静默错：

**① 两趟需要相反的 bank 选择规则。**

| 趟 | 读什么 | 正确的 bank |
|---|---|---|
| pass A（flooding） | 邻居的 **cid**，必须是**本 stage 首值** | 早相位源 ⇒ **镜像**（就是现在那条动态规则） |
| pass B（syncing） | 邻居的 **ptr**，必须是**本 stage pass A 刚提交的值** | **寄存器**（所有 context 的 ptr 在 pass A 已全部提交） |

也就是说：pass A 沿用 §4.8.2 的规则（`源 slice < phase ⇒ 镜像`），
pass B **不能用**那条规则——它对早相位源会读到镜像里的**stage 首值**，
而这里要的恰恰是**已被 pass A 更新过的** ptr。pass B 一律读寄存器。

**② flooding 的跨 context 依赖由 pass A 的镜像规则兜住，这正是分两趟能成立的原因。**
flooding 要读邻居 cid；早相位邻居的寄存器此时已经是本 stage 的新 cid，
所以 pass A 必须走镜像拿到 stage 首值 ✅（现有规则已经如此）。
而 pass B 要的是"邻居**本 stage 算出的** ptr"，此时它一定已经在寄存器里 ✅。
两条需求的 bank 方向相反，这既解释了为什么两趟必须显式实现，也解释了为什么它们各自都自洽。

**③ 可先在"复制版"上验证整套机制（不需要先做合并）。**
把 merging 阶段拆成"A/B 两趟相位"，并让 pass B 用**比较**代替活线抽头：

    nb_push[d]（pass B）= 邻居寄存器的 ptr == 指回本节点的方向
    flip_u/flip_v（pass B）= 端点寄存器的 ptr == 指向对端的方向

这两条**就是**合并版要用的逻辑，而且在复制版上可以独立验证（每 context 仍有自己的 datapath，
所以任何失败都只可能来自"两趟拆法/比较逻辑"，不会与"数据通路合并"混在一起）。
做法：`ifdef SNOW_LAT_2PASS`（默认关），PE 增加 `m_pass`（0=两趟合一，1=只 flooding，2=只 syncing），
阵列在 pass B 用上面的比较，控制器把每个 merging stage 跑成两轮相位
（`busy` 判定要把 A/B 两趟的 busy 或起来；dump 只在 pass B 末尾发一次，保持"一步一个 T 块"）。
**这是合并之前必须先过的一关**；过了它，合并就退化成"把 `CELL` 的编译期下标换成运行时
`slot*NCTX + phase`"的机械改动。

#### 4.8.5 实测结论（两趟已落地、合并已完成；§4.8.4 的一处写法被实测推翻）

**① §4.8.4(a) 的"pass B 一律读寄存器"只对了一半。**
对的是**指针**：pass B 期间源 cell 的寄存器里确实是 pass A 刚提交的 `ptr`。
错的是**整个字**：pass B 自己的提交会用"被替换掉的值"重写镜像，所以
**pass B 期间镜像里装的正是 pass B 的起始值**——它的 `ptr` 就是 pass A 的结果，
而它的 `defect/active` 还是本轮的起始值（pass A 不动这两项）。
⇒ 一次**相位相关**的动态读同时满足两个字段，**零额外读口**；换成裸寄存器读反而会读到
pass B 已经为早相位源更新过的 `defect`。负对照实测：`rep d3 n=2` 由 2314 行变 **2054 行**
（merging 提前退出）⇒ 这条规则是承重的。报告 §6.21.1。

**② §4.8.4 漏了一整个操作数：`!IS_BND`。**
扁平的 push 是 `!IS_BND && defect && (n_ptr != C)`，而 `!IS_BND` 是**生产方**的身份位；
合并后消费者拿不到（源 cell 的下标是运行时值）。先用黄金轨迹回答"它会不会真的起作用"
（`fpga_flow/check_pb_bnd.py`）：**会**——边界节点确实会同时持有 `defect=1` 与 `pointer != C`
（surface d3 `seam` 10 个节点步、surface d5 5 个、surface d5 `seam` 22 个）。
做法：pass A 把**判决**（1 位，`SO_PB`）提交进状态字，消费者只比较指针。
⇒ 状态字宽 `SNOW_PE_STW` +1（寄存器与镜像各一份），**零额外读口**。
（⚠️ 加这一位时踩到：原公式多带一个顶端 slack 位，`OFF_PB = STW-1` 读到了它 ⇒ 一次 push 都没发生。
生成器现在把 `SNOW_PE_STW` 与字段和逐项对账。）

**③ §4.8.4(c) 的"先在复制版上验证"已经做完，但它的证明力有一个上限。**
六个配置（rep d3 / surface d3 / surface d5 × std/`seam`）全部逐行 PASS。
**但复制版 PASS 不能证明合并版可用**：复制版里每个 `(槽位, 切片)` 仍有一套活着的数据通路，
所以把 pass B 换回"活线抽头"**也能 PASS**（实测）。那正是报告 §6.20.9 的结论。

**④ 合并已经完成**（`design/snowflake/snowflake_pe_array_lat1.sv`，一个槽位一个数据通路）：
六条逐行 PASS，且**三条构建（单趟复制版 / 两趟复制版 / 合并版）的轨迹逐字节相同**。报告 §6.22。

**⑤ 合并之后"一个活线抽头都不能留"，而且 `pulse` 不是搬过来、是重算。**
`cell_push[...]` / `cell_pulse[...]` 全消失，`NB_C` / `EB_CU` / `EB_CV` 三张表也随之作废。
替代物都是"生产方**本轮起始状态**"的函数，而那个字消费者本来就在读：
`push` → 提交的 `SO_PB`；`pulse` → 由端点的 `active/whole/grown` 重算
（`GW: ONE_ONE ? active : (active && whole)`；`GH: active && !whole && !grown`）。
⇒ 从"每端点一个 `ESLOT` 路 mux"变成几个门。

**⑥ §6.1 的面积模型要加的第三项**（每 context 常量 ROM / 运行时 mux 的开销）已实测，见报告 §6.22.3。

---### 4.9 状态 bank 的形态（三种都实测过）：**每槽位自己的寄存器 + 一条只读 wire 视图**

合并版的状态该长什么样，是这一轮真正花时间的地方。三种形态都试过，结论是第三种：

| 形态 | 结果（VU9P 综合，`surface`） | 原因 |
|---|---|---|
| ① `reg [STW-1:0] bank [0:MEM-1]`（Verilog **memory**，复制版用的） | `surface d3 n=2` **56 分钟 / 10.2 GB 仍未收敛** | 62 个写口 + 几百个常量地址读口 ⇒ Vivado 按读写组去拆 memory |
| ② **一个模块级 packed 寄存器向量** | `surface d3 n=2` ~10 分钟 / 2.5 GB 出结果；`surface d5 n=2` elaboration 要 **22 GB** ⇒ FAIL | 索引改成常量 part-select 后不再推断 memory，**但 Vivado 会为扇出把寄存器复制到别的实例**（门级日志里一条 `obs_*` 线同时被 `g_slot[0].bank_reg[13]`、`g_eslot[5..8].bank_reg[13]` 驱动） |
| ③ **每槽位自己的寄存器 + 只读 wire 视图**（最终形态） | **`surface d5` 通过 elaboration**；rep d3 LUT −2.5% / FF −21%，surface d3 LUT −3.2% / FF −28% | 寄存器活在自己的 generate 作用域里，别的实例看不到 ⇒ 无从复制；读口取 `bview`（由这些寄存器拼出来的 wire）的常量 part-select |

**三条硬约束（都是踩出来的，写在这里免得再踩）**：

1. **连续赋值的左值必须有常量边界。** `assign bview[<wire 表达式>*STW +: STW] = ...` 非法
   （`Illegal left-hand side in continuous assignment`）⇒ 地址必须在 generate 循环里用
   `localparam` 算出来（每一项都是 `SNOW_LAT_*_VEC[常量]`）。
2. **反过来，读口也不能用"大 wire 上的变量 part-select"。** 形态 ③ 第一版就是这样，
   ModelSim 在 `surface d5` 上**连设计都加载不起来**（`check your system for available memory`
   + `SIGSEGV`，指向 `g_slot[43]/g_dir[8]/g_read[1]`），而 `rep d3`/`surface d3` 没事。
   所以每个端口每个 context 的源地址都必须是常量。
3. **位宽要跟着搬。** 生成器把负偏移**掩码进 `AW` 位**（`_vec`），所以地址算术是
   **模 `2**AW`**；复制版里 `nba` 恰好是 `wire [AW-1:0]`（隐式截断）把这件事藏住了。
   第一次把读口改成常量地址时漏了截断，`rep d3 n=2` 立刻 FAIL（1950/2314）。
   唯一例外是 `absrc`：复制版那一处本来就是全宽索引，所以最终版也**故意**不截断。

**为什么这件事值得单独写一节**：它同时是 §3.4（LUTRAM 化）的前置——
RAM 推断要求**单写口 + 地址可判定**，而形态 ③ 已经天然满足"每个 cell 只有自己的主人写"。

## 5. 上下文调度（复用已验证的 CS 骨架）

- **NCTX = n**，直接沿用已验证的机制：每 context 一份状态、共享数据通路、
  **非抢占仲裁 + drain 拍**（`optimization_report.md` §6.5/6.8：抢占式会死锁，非抢占已逐行验证）。
- 阶段内的执行顺序：`for c in 0..n-1: 执行该 context 的一个阶段`；
  全局 stage 完成条件 = **所有** context 的该阶段都完成（现有 `any_c_busy` 语义要改成"全部完成"）。
- 切换开销：每阶段每 context +2 拍（论文数），一"轮"有 4 个阶段（drop / grow / merge / grow_half+merge），
  所以每轮额外 ≈ 8n 拍。**当 n 大到"每片只有 1 层"时，切换开销会与工作量同量级**——
  这是选择 g 时要把开关开销算进去的原因（§6 表里延迟一列已含粗估）。

### 6.1 ⚠️ 面积律的修正：**状态不随 lattice 缩小**（`fpga_flow/lattice_area_model.py`）

上面那个"1.5–1.7×"仍然是**乐观**的。§0/§6 的估算把整个设计按 `86 LUT × 触及边` 缩放，
隐含假设**全部**面积都随 lattice 变小。实测数据说明这只对**组合逻辑**成立：

1. **状态不会变少，反而可能变多。** 共享 lattice 有 `NSLOT = 最大片` 个槽位，
   每个槽位要存 **n 份** context 状态（一片在跑时其它片的状态必须活着）
   ⇒ 状态总量 = `NSLOT × n ≥ 总节点数`，只有切片均衡时取等号。
2. **多出来的是"context 管理"逻辑，plain 阵列里根本没有这一项。**
   未共享时每个节点的状态就是它自己的触发器，零 mux；共享后 n 个 context 要复用一套 PE，
   每节点每 context 都要读写选择。

两项都能用**已实测的 NCTX 构建**（§6.7，surface d3 PE 阵列，同一 OOC 流程）标定：

| 构建 | LUT | FF | 差值 |
|---|---|---|---|
| plain（无 ctx 设施） | 4,091 | 797 | — |
| NCTX=1 | 4,210 | 808 | **+119 LUT**（第一个 context 的设施，≈3.3 LUT/节点） |
| NCTX=2 | 5,249 | 1,591 | **+1,039 LUT / +783 FF**（每多一个 context ≈28.9 LUT + 21.8 FF/节点） |

21.8 FF/节点 与 plain 构建自身的 22.1 FF/节点 一致 ⇒ **模型是自洽的，不是拟合出来的**。
跨 d 的外推用状态位宽比例 `(CID_W+8)/15`（d3 CID_W=7、d5=9、d7=10、d21=15）；
这个比例**可以先用实测 FF 校验**：预测 d5/d7 的 FF/节点为 d3 的 1.133/1.200 倍，
实测 3,725/150=24.8 与 10,338/392=26.4 对应 **1.122/1.192 倍** ⇒ 比例成立。

用这个模型重算（`python fpga_flow/lattice_area_model.py`）：

| 配置 | naive（节点/最大片） | **状态感知后** | lattice LUT | 其中 ctx 管理 | VU9P 占用 |
|---|---|---|---|---|---|
| surface d3, n=2 | 1.50× | **1.23×** | 3,414 | 23% | 0.3% |
| surface d5, n=2 | 1.67× | **1.41×** | 16,736 | 20% | 1.4% |
| surface d7, n=3 | 2.33× | **1.74×** | 40,287 | 31% | 3.4% |
| **surface d21, n=7** | 7.00× | **3.13×** | **687,322** | **55%** | **58.1%** |

**⇒ §0 表里 d21 g=3/n=7 的"361K LUT / 31%"应修正为 ≈687K LUT / 58%。**
仍然装得下单颗 VU9P，但余量从 69% 掉到 42%，而 §6.12 已经实测过这个设计**在高占用下容易拥塞**。

**更重要的推论：FF 型 context 状态给面积设了一个与 n 无关的下限。**
切片均衡时 `NSLOT ≈ N/n`、`ESLOT ≈ E/n`，于是

```
LUT(n) ≈ 86·0.96·E/n  +  (3.3 + 28.9·(n−1))·(N/n)·sscale
       = 1,770,560/n + 429,830        （surface d21，sscale=1.533）
```

n=3 → 1.02M（86%）、n=7 → 683K（58%）、n=21 → 514K（43%）、**n→∞ → 430K（36%）**。
即 **无论 n 取多大，FF 型状态的共享 lattice 都降不到 ~430K LUT 以下**，
最大共享倍率被钉在 **≈5.0×**（不是 n）。原因很直白：`NSLOT × n` 恒等于总节点数，
所以"每节点一份 context 管理"的总成本与 n 无关。

**这条把 §6.11 的 LUTRAM 判据从"可选优化"变成了"必需项"**：
判据是 `NCTX ≥ 8 或每 PE ≥ 4 节点`（RAM 深度 ≥16），而 **n=7 正好压在门槛上**。
只有把 context 状态放进 LUTRAM（地址位 = context），才能把那 430K 的下限打穿；
否则 snowflake-n 的收益会在 n≈7 附近饱和。
注意 §6.10 已经实测过"给状态寄存器加 `ram_style` 属性"**无效**，
必须重构成真正的 RAM 宏 —— 这是第 4 项工作的实际内容。

**对当前工作的直接影响**：
* d5/n=2 原型的验收线进一步下调到 **≈1.4×**（不是 1.7×，更不是 2×）；
* 原型阶段就该**同时**把状态做成 LUTRAM 形式（哪怕深度只有 2），
  否则测出来的是"FF 型 context 的面积"，对 d21 没有外推价值；
* 选 n 时"越大越好"是错的：**n 的边际收益在 FF 型状态下迅速衰减**，
  真正的自由度是 LUTRAM 之后的 n。

**这个模型还漏了一项成本（诚实列出，并已把它算出量级）**：
NCTX 锚点构建里，所有 context **共用同一张图**，所以每槽位的常量（逻辑 ID、
`is_bnd/is_top/is_bot`、`syn_idx`、每方向的邻居/边索引）仍然是 elaboration 期常量，零成本。
共享 lattice 里它们变成**按相位选择的运行时值**，每一项都要一个 n:1 mux。

先算最坏情况：如果邻居路由也要一张完整的每 context ROM，
d21/n=7 时每槽位需要 `12 方向 × (kind 2 + 邻居槽位 11 + rev 4)` ≈ 204 bit，
再加每方向的边槽位号 12×12 = 144 bit，合计 ≈ 350 bit；7:1 mux 约 3 LUT6/bit
⇒ **~1,050 LUT/槽位 × 1,386 槽位 ≈ 1.45M LUT，超过整颗器件** ⇒ **这条路是死的**。

**但 §1.4 的同构实测正好排除了这个最坏情况**：lattice 本质是规则 3D 网格
（层内 4 邻居 = 固定空间偏移 `(0,±1)(±1,0)`，层间 = `(t±1, 同空间位置)`），
逐层计数完全相同（49/49/36/36），差异**只出现在窗口两端**（3 种端口签名：底/中/顶）。
⇒ **只要槽位编号跟着空间布局走，邻居路由就是常量偏移，不需要 ROM。**
另外核查了 frugal 簇号编码：`SNOW_CID_DELTA(a0)` 的阈值是**对 cid 值**的全局常数
（d5 实测：`default 10; if (a0 >= 50) 20`），**不依赖节点 ID** ⇒ 各片共用同一个函数，
零 per-context 成本（这也正是 §3.2"逻辑 ID 不能重排"要守的东西）。

于是真正需要 per-context ROM 的只剩下（d21/n=7 计）：

| 项 | 位宽 | 为什么躲不掉 |
|---|---|---|
| 逻辑 `ID` | 15 | 复位 cid 与 merging 的 RESET 分支要用它（`snowflake_pe.sv:323/544`） |
| `IS_TOP` / `IS_BOT` | 2 | 指窗口两端，只有首/末片有 |
| `HAS_ABOVE` + above 是否走 seam | 2 | 层间邻居在本片还是跨片，按片不同 |
| above / 邻居的 **seam 索引** | ~9+4 × 2 方向 | 见下面的缓解 |

前三项 ≈ 19 bit ⇒ 约 3 LUT6/bit × 19 ≈ **57 LUT/槽位 × 1,386 ≈ 79K LUT**
（占 §6.1 那个 687K 的 12%——**可以接受，不是致命项**）。
`is_bnd` / `is_syn` / 12 方向邻居槽位 / rev 都是**几何量**，恒定，不进 ROM。

**seam 索引这一项有个现成的缓解**：目前 `make_sliced_sim.py` 按枚举顺序给 seam 条目编号，
所以索引是任意的、必须进 ROM。**如果把 seam 缓冲也按边界层的空间位置编址**
（第 k 个边界槽位 ↔ 第 k 个 seam 条目），索引就退化成常量偏移，这一项直接归零。
这是一个**生成器侧的编号约定**，改动很小，但省掉 d21 上约 100K LUT 量级的 mux
⇒ **实现 lattice 时应当一开始就用几何编址，不要沿用枚举序**。

**这一项没有实测，而且不能靠"第 (a) 步的 no-op 重构"量出来**——只要实例数还是 NN、
选择信号还是 elaboration 期常量，Vivado 会把整个 mux 常量折叠掉，测到的成本恒为 0。
**它只能在真正的共享构建（第 (b) 步，ROM 由 `phase` 这个运行时信号索引）里被量到。**
所以第 (a) 步的定位是**重构检查点**（证明"ID 常量改成端口"不改变语义），不是定价实验。
⇒ 结论：§6.1 表里的 687K 应当读作**下界**，加上 ID/flags 的 ROM 约 **+79K（→ ~766K，65%）**；
如果 seam 索引不做几何编址，还要再加约 100K。

**选择建议**（已按 §6.1 的状态感知面积修正）：

- **VU9P + d21：g=3 / n=7**，但**必须配 LUTRAM 状态**：FF 型是 ≈687K LUT（58%），
  余量只有 42%，而 §6.12 已实测这个设计在高占用下容易拥塞；LUTRAM 化后才能回到
  §6.1 那条 ~312K 组合逻辑 + 少量 RAM 的量级。跨片 9.7% 由 seam 吸收。
- 想要更低延迟可以上 g=7 / n=3（跨片只有 3.2%），但 FF 型是 ≈1.02M LUT（**86%**）——
  基本没有可行性，**除非** LUTRAM 状态先做出来。
- **ZU7EV + d21 在 FF 型状态下不可行**：§6.1 的渐近下限（n→∞）是 ≈430K LUT，
  已经是 ZU7EV（230K）的 1.9 倍。g=1/n=21 那一行的 145K 估算漏掉了 context 管理。
- **n 不是越大越好**：FF 型状态下 `LUT(n) ≈ 1.77M/n + 430K`，n>7 的边际收益很小
  （n=21 也只到 514K）。真正的自由度是 LUTRAM 之后的 n。

**延迟**：**已实测**（报告 §6.25）——
`每轮拍数 = 2 + n × S(d)`，其中 `S(d) = S_nomerge(d) + 2 · S_merge(d)`
（**合并版只在 pass B 提交边 ⇒ 每个 merging stage 花 2 个相位轮**）。
实测：d3 `S = 11.833`（25.67 / 37.50 拍 @ n=2/3）、d5 `S = 12.333`（26.67 / 39.00 / 63.67 拍 @ n=2/3/5），
**rep 与 surface 在同 d 下逐点相同**（只取决于 stage 普查，与图大小无关）。
⚠️ **本段原来的 `≈ n ×（单片执行拍数 + 切换拍数）` 漏掉了两趟 merging 的 ×2**，
所以当时的 "d21 g=3/n=7 ≈4–5× 现状 / ≈355–445 ns/轮" **偏乐观约 1.4×**；
按实测斜率外推：d21/n=7 = **≈89.5–93.0 拍/轮 ⇒ ≈582–605 ns/轮 @6.5 ns**（余量 ≈1.6–1.7× vs ≈1 µs）。

## 7. 验证策略（大 d 不可能全图逐行）

现有能力：与 localuf **逐 timestep/逐阶段/逐提交**逐行比对（RTL + 门级），

   同拍原型（§6.16）与两实例集分时版（§6.18）都保留为**语义参考实现**：
   任何面积共享版本都要在"每全局步一次 dump"的口径下与它们逐行一致。

   **当前状态（2026-09，实测，详见 `optimization_report.md` §6.20）**：

   | 项目 | 结果 |
   |---|---|
   | 结构落地 | ✅ 槽位化阵列 + 四带状态 bank + 每 context 状态体 |
   | 跨缝（第 (c) 步） | ✅ **不需要方案 B**：靠"相位不变性"（本文 §4.8.2）零复制逻辑过缝 |

   | 面积 rep d3（综合） | ⚠️ **1,063 LUT / 437 FF**（扁平基线 924 / 222，LUT **+15.0%**，FF +96.8%） |
   | 时序 rep d3（5 ns） | ⚠️ 5.433 ns / 184.1 MHz / WNS −0.433（基线 195.3 MHz） |
   | 面积 surface d3（综合） | ⚠️ **4,375 LUT / 1,662 FF**（基线 3,992 / 769，LUT **+9.6%**，FF +116%） |
   | 时序 surface d3（5 ns） | ⚠️ 91.8 MHz / WNS −5.889（基线 101.2 MHz / −4.886，两者都未收敛） |
   | LUTRAM 形式 | ⬜ 未做（当前 `bank` 是寄存器数组，d3 规模下综合成 FF） |
   | 面积 surface d5（综合） | 见 `optimization_report.md` §6.20.4 |

   **结论（负结果）**：**n=2 的共享 lattice 比扁平阵列更贵、更慢** —— LUT +15.0% / +9.6%，
   FF 翻倍，时序也退。共享省下的是"数据通路实例数"，花掉的是**每个端口一个相位
   比较器 + 地址 mux**（端口数与 cell 数同阶，开销随实例数线性增长），n=2 摊不薄。
   收益随 NCTX 增长、开销近似不变，所以"从哪个 n 开始划算"必须逐点实测
   （§6.1 面积律还缺的一段，已列入报告 §6.20.7）。§6.1 的"必须用 LUTRAM"
   因此再次被加强：FF 项是线性项，实测里它已经翻倍。

   **⚠️ 一条假结果，必须记住**：`surface d5` 的 lattice 综合一度报出
   **754 LUT / 351 FF / 248.1 MHz**（看起来比 d5 基线 22,620 LUT 小 96.7%），
   但那次运行读到的 lattice 表仍是 `rep d3` 版本——Vivado 综合的是一个
   8 槽位 / 24 边槽位的 **d3** 阵列，而 job 标签写着 d5。综合日志里的
   `NSLOT bound to: 8` / `ES bound to: 24` / `STW bound to: 15` 是铁证
   （d5 应为 90 / 270 / 18）。`synth_lattice.ps1` 已加 **VERIFY 步骤**：
   回读 lattice 头与 graph 头，配置不匹配直接 abort（已用三种配置实测该守卫的
   通过/拒绝行为）。**在修正后的 d5 数字出来之前，面积律外推只能用
   rep d3 / surface d3 两点。**

   这条与其它假结果的成因**不同**——不是工具或仿真器的坑，而是**驱动脚本没有校验
   自己产出的工件**；凡"生成表 → 综合"这种两步流程，都必须在第二步前回读核对。

   **面积律的一条实测修正（更新）**：修对之后 LUT 是**上升**的（+15.0% / +9.6%），
   与 §6.1 原预期相反；**FF 上升 96.8% / 116%** —— 镜像 bank 是**线性项**，
   不能当成常数外推。§6.1 关于"必须用 LUTRAM"的结论因此再次加强。

   **曾经的"唯一阻塞项"（已关闭）**：`above` 源在同 slice 时两个 bank 都不持有
   需要的值。它当时被误判为调度问题，真正原因是 **bank 选择规则差一格**
   （`lattice_b_step_status.md` §3 第 4 条）＋一个把负偏移写成全 1 的生成器缺陷
   （同节第 1 条）。正确规则就是 §4.8.2 的动态 bank 选择；修正后六条逐行回归全过。

   **注意**：面积/时序数字是"该结构形态的成本"。

5. **LUTRAM 化 context 状态**：判据见 §6.11（`NCTX ≥ 8 或每 PE ≥ 4 节点`，即深度 ≥16）。
